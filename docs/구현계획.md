# 전국 공공도서관 통합 검색 사이트 구현 계획

## Context

읽고 싶은 책을 정해 두고도, 자주 가는 도서관 몇 곳 가운데 어디에 그 책이 있는지 확인하려면 도서관 홈페이지를 하나씩 열어서 따로 검색해야 합니다. 특히 한 번 방문해서 여러 권을 함께 빌리려 할 때에는 이 확인 작업이 권수와 도서관 수를 곱한 만큼 늘어나기 때문에, 사실상 매번 포기하게 됩니다.

이 프로젝트는 그 확인 과정을 한 번의 검색으로 줄이는 개인용 도구를 만드는 작업입니다. 미리 선택해 둔 도서관들을 대상으로 책을 검색하면 어느 곳에 소장되어 있는지 알려주고, 상세 정보와 대출 신청은 해당 도서관 페이지로 넘깁니다. 기능을 넓히는 것보다 3단계까지 완주해서 실제로 사용하는 것이 목표입니다.

저장소는 현재 비어 있으므로 이 계획은 전부 신규 작성을 전제로 합니다.

## 1. 데이터 소스 현황 재확인 (2026-09-05 웹 확인)

계획 수립 전에 각 소스의 현재 상태를 웹에서 직접 확인했고, 지시하신 대로 학습 데이터에 의존하지 않았습니다. 확인 결과 제시해 주신 현황은 대부분 정확했으나, 몇 가지 중요한 차이와 새로운 사실을 발견했습니다.

### 확인하여 사실로 확정한 사항

| 소스 | 상태 | 확인된 내용 |
|---|---|---|

| 네이버 책 검색 API | **종료 완료** | 2026-07-31 종료되었고 공식 대체 API가 제공되지 않습니다. NAVER API Hub 이관 대상에서 책 검색이 제외되었습니다. |

### 계획을 바꾸는 새로운 발견 네 가지

**첫째, 정보나루 인증키의 한도 상향 상한은 무제한이 아니라 1일 30,000건입니다.** 2023-11-20부터 무제한 호출이 중단되었고, 서버 IP를 등록하면 1일 500건에서 30,000건으로 확대되는 것이 최대치입니다. 따라서 검색 시점에 API를 호출하는 설계는 애초에 선택지가 될 수 없으며, 벌크 적재와 자체 색인이 선택이 아니라 필수 조건이 됩니다.

**둘째, 전국도서관표준데이터에는 도서관부호가 들어 있지 않습니다.** 이 데이터에는 도서관명과 주소, 위경도는 있지만 도서관부호 항목이 없습니다. 도서관부호를 공통 키로 사용하려는 설계에서 이것은 곧바로 문제가 되므로, 도서관명과 주소를 대조해 두 데이터를 연결하는 별도의 단계가 반드시 필요합니다. 이 대조 작업은 1,604건 규모의 일회성 작업이고 이후에는 확정된 매핑 표를 재사용하면 되므로, 사람이 직접 검수하는 방식을 계획에 포함했습니다.

**셋째, 예스24 Open API는 종료되지 않았고 오히려 확장되었습니다.** 2026-07-15에 신규 서비스가 안내되면서 카테고리 목록, 베스트셀러, 상품 검색, 상품 상세, 작가 정보 조회 기능이 제공되고, Basic 등급의 일일 호출량이 4배로 상향되었습니다. 알라딘과 네이버가 사라진 현재 상황에서 예스24는 사실상 유일하게 남은 상용 도서 API입니다. 1차 범위 밖이라는 지시에 따라 지금은 구현하지 않지만, 후순위 항목 가운데 가장 먼저 붙일 가치가 있는 소스로 재평가할 필요가 있습니다.

**넷째, 관리형 PostgreSQL의 한국어 검색 확장 상황이 최근 크게 바뀌었습니다.** Neon의 `pg_search`는 2026-03-19부터 신규 프로젝트에서 제공이 중단되었고, **2026-09-21에 기존 프로젝트에서도 제거될 예정입니다.** 지금부터 16일 뒤이므로 이 확장에 의존하는 설계는 세워서는 안 됩니다. 반면 **Supabase는 PGroonga를 공식 지원**하며, PGroonga는 한국어를 포함한 비 라틴 문자권 전문 검색을 처리합니다. 이 사실이 아래의 검색 계층 선택을 결정했습니다.

### 확인하지 못한 사항 (1단계 착수 시 직접 검증 필요)

이 세션의 네트워크 정책이 `data4library.kr`, `nl.go.kr`, `data.go.kr` 도메인에 대한 접근을 차단하고 있어서, 공식 문서 원문을 직접 열어보지 못했습니다. 우회하지 않고 검색 결과와 2차 자료로 확인했으므로, 아래 항목은 **1단계 첫 작업인 사전 검증 단계에서 반드시 직접 확인해야 합니다.** 계획의 나머지 부분은 이 검증 결과에 따라 세부 조정될 수 있습니다.

- 정보나루 장서 데이터 벌크 파일의 정확한 컬럼 구성과 ISBN13 포함 여부
- 1,604개관의 벌크 파일을 스크립트로 내려받을 수 있는지, 아니면 화면에서 개별 선택해야 하는지
- 도서관 한 곳의 장서 파일 실제 용량과 행 수
- ISBN 서지정보 API 응답의 전체 필드 목록과 일일 호출 한도
- 정보나루 `libCode`가 국립중앙도서관 도서관부호와 동일한 체계인지 여부

## 2. 기술 스택 선택과 근거

확인해 주신 선택(전국 1,604개관 전부, 관리형 서비스 조합, Spring Boot 유지, 1차에는 표지 없음)을 반영한 구성입니다.

| 계층 | 선택 | 근거 |
|---|---|---|
| 프론트엔드 | React 19 + TypeScript + Vite | 이미 익숙한 스택이고, 이 프로젝트의 화면은 SEO나 서버 렌더링이 필요하지 않은 도구형 화면이므로 SPA로 충분합니다. |
| 프론트 배포 | Cloudflare Pages | 정적 자산만 올리면 되고 무료 등급으로 충분합니다. |
| 백엔드 | Java 21 + Spring Boot 3.x | 익숙한 스택을 유지하는 것이 완주 가능성을 가장 높입니다. 이 프로젝트는 화면보다 적재 배치가 작업량의 대부분인데, 대용량 CSV 적재와 재시도, 실패 격리는 Spring Batch가 이미 잘 다루는 영역입니다. |
| API 서버 배포 | Fly.io 컨테이너 | 상시 가동이 필요한 부분은 조회 API뿐이고 요청량이 매우 적으므로 최소 사양으로 충분합니다. |
| DB 및 색인 | **Supabase PostgreSQL (Pro) + PGroonga** | 아래에 따로 설명합니다. |
| 원본 아카이브 | Cloudflare R2 | S3 호환이면서 무료 등급이 10GB이고 조회 시 전송 비용이 없습니다. 내려받은 원본 파일을 그대로 보관하는 용도입니다. |
| 적재 배치 실행 | GitHub Actions 예약 작업 | 월 1회 몇 시간 도는 작업 때문에 상시 서버를 키워 두는 것은 낭비입니다. 배치 전용 프로파일로 같은 코드를 실행합니다. |

**월 운영 비용은 약 25~30달러로 예상합니다.** Supabase Pro가 25달러이고 나머지는 무료 등급 안에서 처리됩니다.

### 검색 엔진을 따로 두지 않는 이유

검토 요청하신 핵심 질문에 대한 결론은 **별도 검색 엔진을 두지 않고 PostgreSQL 하나로 색인까지 겸한다**입니다. 근거는 세 가지입니다.

첫째, 규모가 별도 엔진을 요구하는 수준이 아닙니다. 아래 3절에서 추정하듯 검색 대상 서지 문서는 350만 건 안팎이고, 이는 PostgreSQL이 편하게 다루는 범위입니다. 색인이 커지는 원인은 서지가 아니라 소장 관계인데, 소장 관계는 전문 검색 대상이 아니라 교집합 연산 대상이므로 검색 엔진이 필요한 부분이 아닙니다.

둘째, Elasticsearch나 OpenSearch를 Nori 형태소 분석기와 함께 운영하려면 그 자체로 8GB RAM과 4코어가 권장 사양입니다. 사용자가 몇 명인 도구에 이만큼의 상시 자원을 붙이면 운영 비용이 나머지 전부를 합친 것보다 커지고, 구성 요소가 하나 늘어나는 만큼 완주 가능성도 떨어집니다.

셋째, 한국어 처리라는 관건이 PGroonga로 해결됩니다. PGroonga의 `TokenBigram` 토크나이저는 사전 없이 2글자 단위로 색인하므로 형태소 분석기의 사전 관리 부담이 없습니다. 도서 제목 검색이라는 이 프로젝트의 용도에서는 이 방식이 오히려 유리한데, 형태소 분석기가 복합명사를 잘못 분리해서 검색이 실패하는 경우가 도서 제목에서 특히 자주 발생하기 때문입니다. 정밀도는 형태소 분석 방식이 높고 재현율은 바이그램 방식이 높은데, 이 도구에서는 "찾고 있는 책이 안 나오는 것"이 "관련 없는 책이 섞여 나오는 것"보다 훨씬 치명적이므로 재현율을 택하는 것이 맞습니다.

### 검색 계층의 이탈 대비책

알라딘과 네이버가 두 달 사이에 사라졌고, Neon의 `pg_search`도 예고 후 6개월 만에 제거됩니다. 소스뿐 아니라 인프라 구성 요소도 사라진다는 것을 전제해야 합니다. 따라서 **정규화와 토큰화 로직을 PGroonga에 위임하지 않고 우리 코드에 두겠습니다.** 구체적으로는 적재 단계에서 정규화한 `search_text` 컬럼을 만들어 두고, 여기에 PGroonga 색인을 겁니다. PGroonga를 쓸 수 없게 되면 같은 `search_text`에 대해 우리가 직접 생성한 바이그램을 `simple` 설정의 `tsvector`로 색인하는 방식으로 전환할 수 있고, 이 전환은 색인 정의와 질의 생성부만 바꾸면 되므로 스키마 변경이나 재적재가 필요 없습니다.

## 3. 색인 대상 데이터 규모 추정

정보나루 집계값(1,604개관, 장서 202,890,000권)에서 출발해 단계별로 환산했습니다. 각 가정은 1단계 사전 검증에서 실측으로 교체해야 합니다.

| 단계 | 값 | 가정 |
|---|---|---|
| 전체 장서 권수 | 202,890,000권 | 정보나루 집계값 |
| 복본 제거 후 관내 고유 종수 합계 | 약 156,000,000 | 공공도서관 복본율 1.3 가정 |
| ISBN 보유분만 남긴 소장 관계 | **약 120,000,000** | 1991년 이전 도서, 비도서, 연속간행물 등 20% 제외 가정 |
| 전국 고유 ISBN13 서지 | **약 3,500,000** | 국내 ISBN 발행 누적과 번역서를 포함한 추정 |
| 동일성 판별 후 저작 단위 | 약 2,000,000 | 판본과 표기 차이를 묶은 뒤 |
| 도서관 1곳당 평균 고유 종수 | 약 78,000 | 156,000,000 ÷ 1,604 |
| 책 1권당 평균 소장 도서관 수 | **약 34** | 120,000,000 ÷ 3,500,000 |

### 이 추정이 설계에 미치는 결정적 영향

마지막 줄이 핵심입니다. 소장 관계를 `(도서관 ID, 책 ID)` 두 컬럼 테이블로 정규화해 저장하면 1억 2천만 행이 되고, PostgreSQL의 행당 오버헤드를 고려하면 힙만 약 5GB, 조회용 인덱스까지 더하면 **10~15GB**가 됩니다. Supabase Pro의 기본 포함 용량 8GB를 넘고, 저장 비용보다 더 큰 문제는 **연산 자원**입니다. 1억 2천만 행 인덱스를 1GB RAM의 기본 인스턴스로 조회하면 인덱스가 메모리에 올라가지 않아 매 질의가 디스크를 읽게 되고, 월 1회 전량 재적재도 몇 시간 단위로 늘어집니다. 인스턴스를 4~8GB로 올리면 월 60~110달러가 추가됩니다.

그래서 **소장 색인을 책 단위로 접어서 저장하는 방식을 제안합니다.** 책 한 권당 한 행을 두고, 그 책을 소장한 도서관 ID 목록을 배열로 담습니다. 도서관이 1,604곳뿐이므로 도서관 ID는 `SMALLINT`(2바이트)에 들어갑니다.

```
소장색인(book_id INT PRIMARY KEY, lib_ids SMALLINT[])
```

책 1권당 평균 34개 도서관이므로 배열은 평균 68바이트이고, 행 오버헤드를 더해도 행당 약 120바이트입니다. 350만 행이면 **약 400MB**로, 정규화 방식 대비 30배 이상 줄어듭니다. 전체 DB가 4~5GB 안에 들어와 Supabase Pro 기본 용량과 최소 인스턴스로 감당됩니다.

성능 면에서 더 중요한 것은 질의 형태가 바뀐다는 점입니다. "선택한 도서관 중 이 책을 소장한 곳"은 한 행을 읽어 배열을 교집합하는 연산이 되고, "여러 권을 도서관별로 집계"는 책 수만큼의 행을 읽어 각각 교집합한 뒤 세는 연산이 됩니다. 30권을 20개 도서관에 대해 확인해도 읽는 행은 30개입니다. 조인으로 1억 2천만 행을 훑는 것과는 비교가 되지 않습니다.

이 방식의 대가는 "특정 도서관이 소장한 책 목록"을 뽑는 질의가 비효율적이라는 점인데, 1~3단계 어디에도 그 기능이 없으므로 지금은 비용이 아닙니다.

### "DB가 원본, 색인은 파생" 원칙의 적용

제시하신 원칙을 그대로 지키되, 원본 계층을 두 층으로 나눕니다.

1. **원본 아카이브 (Cloudflare R2)**: 내려받은 월별 벌크 파일을 가공하지 않고 gzip으로 압축해 보관합니다. 소스가 사라져도 복구가 가능해야 한다는 요구를 실제로 충족하는 것은 이 계층입니다. 정보나루가 내일 문을 닫아도 우리가 받아 둔 파일은 남습니다.
2. **DB (정규화 원본)**: 도서관 마스터, 서지, 적재 이력, 리다이렉트 템플릿, 링크 점검 결과를 정규화해 보관합니다.
3. **색인 (파생)**: 위의 소장 색인과 검색용 서지 문서. 언제든 1과 2에서 다시 만들 수 있습니다.

이렇게 하면 스키마를 바꾸거나 재색인할 때 소스에 다시 호출하지 않아도 된다는 요구가 충족되고, 1억 2천만 행을 관리형 DB에 상시 올려 두는 비용은 치르지 않게 됩니다. 나중에 정규화 소장 테이블이 DB에 꼭 필요해지면 시도 단위로 파티션을 나눠 추가할 수 있고, 그때도 색인 구조는 바뀌지 않습니다.

## 4. DB 스키마와 색인 문서 구조

### 도서관 마스터

`library` 테이블은 도서관부호를 자연 키로 삼고, 색인 배열에 넣을 2바이트 내부 ID를 따로 둡니다.

```sql
CREATE TABLE library (
  lib_code        VARCHAR(20) PRIMARY KEY,   -- 도서관부호 (예: '011001')
  short_id        SMALLINT    NOT NULL UNIQUE, -- 소장 색인 배열용 내부 ID
  name            TEXT        NOT NULL,
  name_norm       TEXT        NOT NULL,      -- 매칭 및 이름 검색용 정규화 표기
  lib_type        TEXT,                      -- 관종
  sido            TEXT        NOT NULL,
  sigungu         TEXT        NOT NULL,
  address_road    TEXT,
  latitude        DOUBLE PRECISION,
  longitude       DOUBLE PRECISION,
  homepage_url    TEXT,
  phone           TEXT,
  closed_days     TEXT,                      -- 휴관일
  open_hours      JSONB,                     -- 평일/토요일/공휴일 운영시각
  d4l_lib_code    TEXT,                      -- 정보나루 코드 (부호와 다를 경우 대비)
  std_match_score REAL,                      -- 표준데이터 대조 신뢰도
  std_match_state TEXT NOT NULL DEFAULT 'unmatched', -- auto|manual|unmatched
  holdings_state  TEXT NOT NULL DEFAULT 'pending',   -- pending|indexed|failed
  holdings_as_of  DATE,                      -- 이 도서관 소장 데이터의 기준 시점
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON library (sido, sigungu);
CREATE INDEX ON library USING gist (ll_to_earth(latitude, longitude)); -- 내 주변 탐색
```

`std_match_state`와 `holdings_state`가 운영상 중요합니다. 앞의 것은 1절에서 지적한 표준데이터 대조 문제를 추적하고, 뒤의 것은 어떤 도서관의 소장 데이터가 아직 없는지를 화면에서 정직하게 표시하기 위한 것입니다.

### 서지와 저작

판본과 표기 차이로 흩어진 레코드를 묶기 위해 저작(work)과 서지(book) 두 층으로 나눕니다. 사용자가 검색하는 대상은 저작이고, 도서관이 소장하는 대상은 서지입니다.

```sql
CREATE TABLE work (

  match_key     TEXT NOT NULL UNIQUE,   -- 정규화 매칭 키

  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE book (
  book_id       INTEGER PRIMARY KEY,
  isbn13        CHAR(13) NOT NULL UNIQUE,
  isbn10        CHAR(10),
  set_isbn13    CHAR(13),               -- 세트 ISBN (낱권과 구분)
  work_id       INTEGER REFERENCES work,
  title         TEXT NOT NULL,
  subtitle      TEXT,
  series_title  TEXT,
  author_raw    TEXT,
  publisher_raw TEXT,
  pub_date      DATE,
  price         INTEGER,
  page_count    INTEGER,
  kdc           TEXT,
  keywords      TEXT,
  title_norm     TEXT NOT NULL,          -- 정규화 결과 (6절)
  author_norm    TEXT,
  publisher_norm TEXT,
  source_key     TEXT NOT NULL,          -- 어느 어댑터가 넣었는지
  source_fetched_at TIMESTAMPTZ NOT NULL

```

### 검색 색인 문서

"색인 조회 한 번으로 결과 화면을 그릴 수 있어야 한다"는 요구에 맞춰, 검색과 결과 표시에 필요한 모든 것을 한 테이블에 비정규화합니다. 소장 도서관 배열까지 여기에 넣기 때문에 검색 결과 한 건을 그리는 데 추가 조회가 필요 없습니다.

```sql
CREATE TABLE search_doc_v1 (
  work_id        INTEGER PRIMARY KEY,
  title_display  TEXT NOT NULL,
  author_display TEXT,
  publisher_display TEXT,
  pub_date       DATE,
  price          INTEGER,
  isbn13_list    CHAR(13)[] NOT NULL,   -- 이 저작에 묶인 모든 판본
  lib_ids        SMALLINT[] NOT NULL,   -- 소장 도서관 short_id 집합 (정렬됨)
  lib_count      SMALLINT  NOT NULL,
  as_of_date     DATE      NOT NULL,    -- 화면에 표기할 기준 시점
  search_text    TEXT      NOT NULL     -- 정규화된 검색 대상 텍스트
);

CREATE INDEX ON search_doc_v1 USING pgroonga (search_text);
CREATE INDEX ON search_doc_v1 USING gin (isbn13_list);
CREATE INDEX ON search_doc_v1 USING gin (lib_ids);
```

### 별칭 전환에 의한 무중단 재색인

Elasticsearch의 별칭에 해당하는 것을 PostgreSQL에서는 **뷰**로 구현합니다. 애플리케이션은 언제나 `search_doc`만 조회하고, 실제 테이블 이름은 알지 못합니다.

```sql
CREATE VIEW search_doc AS SELECT * FROM search_doc_v1;

-- 재색인: search_doc_v2를 처음부터 새로 만들어 채우고 색인까지 건 뒤
CREATE OR REPLACE VIEW search_doc AS SELECT * FROM search_doc_v2;  -- 원자적 전환
DROP TABLE search_doc_v1;  -- 충분히 지켜본 뒤에 정리
```

`CREATE OR REPLACE VIEW`는 트랜잭션 안에서 원자적으로 처리되므로 조회가 끊기지 않습니다. 새 테이블을 채우는 동안 기존 테이블은 그대로 서비스하며, 실패하면 전환하지 않고 버리면 되므로 되돌리기도 간단합니다. 처음부터 이 구조로 시작해야 나중에 스키마를 바꿀 때 고생하지 않습니다.

## 5. 한국어 검색 품질 확보 방안

검색은 아래 순서로 단계를 낮춰 가며 시도하고, 결과가 나온 단계에서 멈춥니다. 사용자가 원하는 책을 못 찾고 빈 화면을 보는 것이 이 도구를 버리게 만드는 가장 큰 요인이므로, 실패했을 때 그냥 끝내지 않고 다음 단계로 넘어가는 것이 중요합니다.

1. **ISBN 직접 일치**: 입력이 10자리 또는 13자리 숫자 형태이면 `isbn13_list` 배열을 조회합니다. ISBN-10은 13자리로 변환한 뒤 대조합니다.
2. **PGroonga 전문 검색**: `search_text`에 대해 `&@~` 연산자로 질의하고 `pgroonga_score`로 정렬합니다. `search_text`는 제목, 부제, 시리즈명, 저자, 출판사를 정규화해 이어 붙인 텍스트입니다.
3. **유사도 보정**: 위에서 결과가 없으면 `pg_trgm`의 `similarity(title_norm, 질의)`로 임계값 이상인 것을 찾습니다. 오타와 띄어쓰기 오류를 여기서 흡수합니다.

정규화 규칙은 6절의 서지 정규화와 **동일한 함수를 공유합니다.** 색인할 때와 질의할 때 서로 다른 정규화를 적용하면 조용히 어긋나기 때문에, 정규화 함수는 한 곳에만 두고 양쪽에서 호출합니다.

동의어와 저자명 이표기는 사전 테이블로 관리합니다. 자동 추출을 시도하면 오탐이 늘고 검증이 어려우므로, 실제로 검색에 실패한 사례를 보고 손으로 추가하는 방식이 이 규모에서는 더 낫습니다.

```sql
CREATE TABLE search_synonym (
  term      TEXT NOT NULL,   -- 사용자가 입력할 법한 표기
  canonical TEXT NOT NULL,   -- 색인에 들어간 정규 표기
  kind      TEXT NOT NULL,   -- title|author|publisher
  PRIMARY KEY (term, kind)
);
```

예를 들어 `('제이케이롤링', '조앤케이롤링', 'author')`, `('해리포터', '해리포터', 'title')`처럼 채웁니다. 질의 시 사전을 먼저 적용해 정규 표기로 바꾼 뒤 검색합니다.

## 6. 도서관 선택 화면

### 세 가지 탐색 경로

**내 주변**은 브라우저 위치 권한을 받아 `library` 테이블의 위경도로 거리순 정렬합니다. 위경도는 전국도서관표준데이터에서 오므로, 1절에서 지적한 대조 실패 도서관은 위경도가 비어 이 경로에 나타나지 않습니다. 그런 도서관은 이름 검색과 지역 계층에서는 정상적으로 찾을 수 있어야 하므로, 위경도 유무와 무관하게 목록에 포함시킵니다. 위치 권한을 거부하면 이 탭은 시도 선택으로 대체합니다.

**이름 검색**은 `name_norm`에 대한 부분 일치로 처리합니다. 1,604건뿐이므로 전체를 프론트로 내려보내고 클라이언트에서 필터링해도 됩니다. 실제로 이 편이 응답이 즉각적이라 사용감이 좋고, 지역 계층 화면도 같은 데이터로 그릴 수 있습니다. 전체 목록은 약 1,604행 × 200바이트 정도이므로 gzip 후 100KB 미만입니다.

**지역 계층**은 시도 > 시군구 > 도서관 3단계로 접었다 펴는 목록입니다.

### 세 상태 체크박스

상위 계층은 전체 선택, 부분 선택, 미선택 세 상태를 가집니다. React에서 `indeterminate`는 속성이 아니라 DOM 프로퍼티이므로 JSX로 직접 지정할 수 없고, `ref`를 통해 설정해야 합니다.

```tsx
function TriStateCheckbox({ state, onChange }: { state: 'all' | 'some' | 'none'; onChange: () => void }) {
  const ref = useRef<HTMLInputElement>(null);
  useEffect(() => {
    if (ref.current) ref.current.indeterminate = state === 'some';
  }, [state]);
  return <input ref={ref} type="checkbox" checked={state === 'all'} onChange={onChange} />;
}
```

선택 상태는 **선택된 도서관부호의 집합 하나만을 유일한 원본으로 두고**, 시군구와 시도의 세 상태는 그 집합에서 매번 계산합니다. 상위 계층의 상태를 따로 저장하면 하위와 어긋나는 순간 복구가 어려워집니다. 하위가 모두 선택되면 상위가 자동으로 체크되는 동작은 이 계산 방식에서 저절로 따라옵니다.

### 저장과 URL 표현

선택 결과는 로그인 없이 `localStorage`에 보관하고, 동시에 URL 쿼리로도 표현합니다. 두 곳의 우선순위는 **URL이 있으면 URL이 이깁니다.** 공유받은 링크를 열었을 때 내 기존 선택으로 덮이면 공유가 의미를 잃기 때문입니다.

URL에는 도서관부호를 그대로 나열하지 않습니다. 20곳만 선택해도 부호가 6자리씩이라 URL이 길어집니다. 대신 `short_id`를 36진수로 바꿔 쉼표로 잇습니다.

- 기본 방식: `?libs=1a,2f,x3,...` — 20곳이면 약 60자입니다.
- 100곳을 넘으면 비트맵 방식으로 전환합니다: `?libsb=<base64url>` — 1,604비트는 201바이트이므로 base64url로 268자이고, 몇 곳을 고르든 길이가 일정합니다.

`short_id`는 내부 ID이므로 재적재 과정에서 값이 바뀌면 공유된 링크가 전부 깨집니다. **`short_id`는 한 번 발급하면 절대 재사용하지 않고 변경하지도 않는다**는 규칙을 스키마 주석과 `CLAUDE.md`에 명시하겠습니다.

### 많이 선택했을 때의 결과 표시

상한을 두지 않는 대신 결과 화면에서 소화합니다. 소장 도서관이 많을 때는 기본적으로 시군구 단위로 묶어 접고, 위치 권한이 있으면 거리순으로 가까운 3곳을 펼쳐 둡니다. 위치 권한이 없으면 사용자가 선택 화면에서 마지막으로 사용한 정렬 기준을 따릅니다. 전체 목록은 접힌 부분을 펼쳐 확인합니다.

## 7. 서지 정규화와 도서 동일성 판별

이 프로젝트에서 가장 어려운 부분이고, 잘못 만들면 조용히 틀린 결과를 내놓기 때문에 검증 가능한 형태로 만드는 것이 중요합니다.

### 판단의 기준: 누락이 오병합보다 낫습니다

먼저 방향을 정해 둡니다. **누락을 택합니다.** 누락은 실제로 소장한 책을 "미소장"으로 보여주는 것이라 사용자가 도서관 페이지에서 직접 확인하면 바로잡히고, 무엇보다 눈에 보입니다. 반면 오병합은 다른 책을 "소장"으로 보여주어 헛걸음을 만들고, 두 저작이 이후의 모든 검색에서 계속 붙어 다니는데도 아무도 눈치채지 못합니다. 규칙을 조일지 풀지 고민될 때는 조이는 쪽을 택합니다.

### A단계: 정규화 이전에 필드를 분리합니다

정보나루 벌크 데이터의 `bookname`과 `authors`에는 KORMARC 245 필드의 구분 기호가 그대로 섞여 들어옵니다. 이것을 먼저 분리하지 않고 정규화하면 쓰레기를 정규화하게 됩니다.

```
원본: "해리 포터와 마법사의 돌 = Harry Potter and the sorcerer's stone : 1부 / J.K. 롤링 지음 ; 강동혁 옮김"

A1. 첫 " / " 에서 분리        → 표제부 | 책임표시부
A2. 표제부를 " = " 에서 분리   → 본표제 | 대등표제(별칭 키로 보관)
A3. 본표제를 " : " 에서 분리   → 표제 | 부표제
A4. 표제 끝의 권차를 분리      → vol_no
      /[\s.]*(제)?\s*(\d+|[IVXivx]+)\s*(권|부|편|화|집)?\s*$/, `(상)|(중)|(하)|상권|하권`
A5. 끝의 괄호 안 판사항을 분리 → edition_tokens[]
A6. 각색 표기를 탐지          → adaptation_tokens[]
```

저자는 **세미콜론으로 먼저 나눕니다.** 쉼표는 목록 구분자가 아니라 도치 구분자이기 때문입니다.

```
"조앤 K. 롤링 지음 ; 강동혁 옮김" → [{조앤 K. 롤링, 저자}, {강동혁, 역자}]
"롤링, 조앤 캐슬린"               → [{롤링 조앤 캐슬린, 저자}]   ← 쉼표는 도치, 목록이 아님
```

역할어 목록은 `지음 저 저자 글 씀 엮음 엮은이 편 편저 편역 옮김 역 번역 옮긴이 그림 그린이 사진 감수 해설 각색 원작 만화 기획 著 編 譯`입니다. **매칭 키에는 저자와 원저자 역할만 넣습니다.** 역자는 판본마다 다른데, 역자가 다른 판본이야말로 묶고 싶은 대상이기 때문입니다.

### B단계: 판본 표기와 각색 표기를 구분합니다

이것이 오병합 품질의 대부분을 결정합니다. 두 목록을 혼동하면 잘못된 묶음이 쏟아집니다.

- **판본 표기 (제거하고 묶음)**: `개정판 개정증보판 증보판 전면개정판 개역판 신판 초판 재판 제2판 2판 양장본 양장 반양장 무선 보급판 문고판 특별판 한정판 리커버 합본판 완역본`
  같은 내용의 다른 인쇄이므로 **묶어야 합니다.** 화면에는 "코스모스 · 특별판 (2010)"처럼 표시만 다르게 합니다.
- **각색 표기 (묶지 않는 근거로 사용)**: `만화 만화로보는 청소년판 어린이 그림책 요약 축약본 쉽게읽는 큰글자책 큰글씨책 점자 오디오북 전자책 영어판 일본어판 원서 대활자본`
  내용이 다른 별개의 저작이므로 **절대 묶으면 안 됩니다.** 「데미안」과 「데미안(청소년판)」은 정규화하면 키가 같아지므로, 각색 표기를 별도로 붙잡아 두고 병합을 거부하는 근거로 씁니다.

권차도 같은 이유로 키에 남깁니다. `미움받을 용기`와 `미움받을 용기 2`는 다른 책입니다.

나머지 정규화 순서는 아래와 같습니다.

```
1. NFKC 정규화 (전각→반각, Ⅲ→III, ①→1)
2. 영문 소문자 변환
3. 한글 뒤 괄호 안 한자는 키에서 제거하고 별칭 키로 보관
     "난중일기(亂中日記)" → 키 "난중일기", 별칭 "亂中日記"
4. 공백 전부 제거          ← 단일 규칙 중 효과가 가장 큽니다
5. 구두점 제거: · ‧ ・ , . - – — ~ ! ? ' " ( ) [ ] 《 》 「 」 : ; / \ & + * _
6. 끝의 단독 로마숫자를 아라비아숫자로 변환
7. 판본 표기 제거 (위 목록)
```

키는 셋을 만듭니다. `title_key_core`(표제만, 군집화용), `title_key_full`(표제+부표제, 점수 계산용), `alias_key[]`(대등표제·한자형·미분리형, 후보 묶기용). 별칭 키가 있어야 「난중일기(亂中日記)」와 「亂中日記」가 같은 후보 묶음에 들어갑니다.

### 저자 대조는 문자열 비교가 아니라 토큰 집합으로 합니다

외국인 이름의 한글 음차는 문자열로 맞출 수 없습니다. 시도하지 않는 편이 낫습니다.

```
"조앤 K. 롤링"     → {조앤, k, 롤링}
"J.K.롤링"         → {j, k, 롤링}
"롤링, 조앤 K."    → {롤링, 조앤, k}
```

```java
boolean authorCompatible(a, b) {
    if (a.tokens.isEmpty() || b.tokens.isEmpty()) return UNKNOWN;  // 막지 말고 등급을 낮춤
    var shared = intersect(a.tokens, b.tokens);
    if (shared.isEmpty()) return false;
    if (shared.stream().anyMatch(t -> corpusDf(t) < 0.001)) return true;  // 희소 토큰은 결정적
    return jaccard(a.tokens, b.tokens) >= 0.5;
}
```

`corpusDf`는 저자 토큰의 출현 빈도표이고 군집화할 때마다 다시 만듭니다. `롤링`은 빈도가 0.0002라 그것 하나로 동일인을 확정할 수 있지만, `김`은 빈도가 0.2라 아무것도 확정하지 못합니다. **이 빈도표가 있어야 한국어 저자명 대조가 성립합니다.**

### C단계: ISBN을 신뢰하되 검증합니다

국내 데이터에는 ISBN 필드에 부가기호가 섞여 들어오는 경우가 흔합니다.

```
C1. 영숫자만 남기고 13자리를 초과하면 앞 13자리를 취합니다.
      "9788983920775 03840" → "9788983920775"      ← 부가기호 오염
C2. 체크디지트를 검증하고 ISBN-10은 13자리로 변환합니다. 원본도 함께 보관합니다.
C3. 배제: 같은 숫자 반복, 접두가 978/979가 아닌 것, 길이 불일치
```

그리고 **같은 ISBN이라도 제목이 전혀 다르면 병합하지 않습니다.** 등록번호 오입력이나 복사 실수로 같은 ISBN에 다른 제목이 붙은 레코드가 실제로 존재합니다.

```
같은 isbn13인데 제목 유사도 < 0.5  →  ISBN_CONFLICT로 표시하고 검토 큐에 넣습니다.
신뢰도가 높은 소스(서지정보 API)의 필드를 유지하고, 낮은 소스가 덮어쓰지 못하게 합니다.
```

세트 ISBN은 낱권과 별개의 레코드로 두고 `bib_set_member(set_isbn13, member_isbn13, seq)`로 연결만 합니다. 세트를 낱권 저작에 직접 병합하면 "3권을 소장"과 "전집을 소장"이 구분되지 않습니다.

### D단계: 후보 묶기 + 규칙 판정 + union-find

단일 해시 키로 묶지 않습니다. 필드 하나만 달라도 놓치고, 왜 그렇게 묶였는지 설명할 수 없기 때문입니다.

**후보 묶기**는 `title_key_core` 완전 일치, 각 `alias_key` 완전 일치, `title_key_core` 앞 8글자로 합니다. 한 묶음이 500건을 넘으면(「국어」, 「일기」 같은 흔한 제목) 엄격한 규칙만 적용합니다.

**판정 규칙**은 위에서부터 순서대로 평가합니다.

```
R0  isbn13 동일 && 권차 동일                              → 병합 1.00
R1  권차 불일치                                           → 거부
R2  각색 표기 불일치 || 언어 불일치                       → 거부
R3  title_key_core 동일 && authorCompatible               → 병합 0.95
R4  title_key_full 동일 && authorCompatible               → 병합 0.93
R5  title_key_core 동일 && 한쪽 저자 없음
      && 출판사 동일 && |발행연도 차| <= 1                → 병합 0.80
R6  title_key_core 동일 && authorCompatible == false      → 검토 0.55
R7  제목 유사도 >= 0.92 && authorCompatible               → 검토 0.60 (기본 비활성)
그 외                                                     → 거부
```

권차는 양쪽 다 없으면 호환이고, 한쪽만 있으면 불일치입니다(「토지 1」과 「토지」를 막습니다). 출판사는 키에 넣지 않습니다. 출판사를 옮겨 재출간하는 경우가 흔하고, 그것은 묶고 싶은 대상이기 때문입니다.

**병합 판정만 union-find로 합치고, 검토 판정은 합치지 않고 큐에 쌓습니다.** 350만 노드 정도는 `int[]` 배열로 수백 MB 안에서 몇 초에 끝납니다.

판정 근거는 반드시 남깁니다. 이것이 있어야 잘못된 묶음을 진단할 수 있습니다.

```sql
CREATE TABLE bib_merge_edge (
  a_book_id INTEGER, b_book_id INTEGER,
  rule_code TEXT NOT NULL, confidence NUMERIC NOT NULL, run_id BIGINT,
  PRIMARY KEY (a_book_id, b_book_id)
);
```

### work_id를 안정적으로 유지합니다

**`work_id`는 공유 URL에 들어갑니다.** 재군집화 때 번호가 새로 매겨지면 공유된 링크가 전부 조용히 깨집니다. 6절의 `short_id`와 같은 문제입니다.

```
새 군집 C마다:
    prev = C의 구성원들이 이전에 갖고 있던 work_id의 최빈값
    prev가 있고 이번 실행에서 아직 쓰이지 않았으면 그대로 재사용
    아니면 새 번호를 발급
    C 안의 다른 이전 work_id p는 bib_work_alias(p → 배정된 id)에 기록
```

`GET /work/{id}`는 별칭 표를 거쳐 해석하고 301로 넘깁니다. 20줄이면 되고, 없으면 절대 발견하지 못할 종류의 버그를 막습니다.

### 적용 예시

| 상황 | 판정 |

### 잘못된 묶음을 고치는 경로

자동 판별은 반드시 틀립니다. 값싸게 고칠 수 있어야 실제로 쓸 수 있습니다.

```sql
CREATE TABLE bib_merge_override (
  a_isbn13 CHAR(13) NOT NULL, b_isbn13 CHAR(13) NOT NULL,
  verdict  TEXT NOT NULL,   -- FORCE_MERGE | FORCE_SPLIT
  note     TEXT,
  PRIMARY KEY (a_isbn13, b_isbn13)
);
```

군집화는 `FORCE_SPLIT` 쌍을 간선 집합에서 먼저 제거하고 `FORCE_MERGE`를 신뢰도 1.0으로 추가한 뒤 실행합니다. 분리 지정한 쌍이 제3의 레코드를 거쳐 여전히 같은 군집에 남아 있으면, 두 레코드 사이 최단 경로에서 신뢰도가 가장 낮은 간선을 끊고 다시 실행합니다. 5회까지 반복하고 그래도 남으면 기록만 남깁니다.

**고치는 화면을 반드시 만듭니다.** `/admin/works/{id}`에 판본 목록과 "이 판본 분리" 버튼을 두는 한 페이지짜리 화면입니다. SQL을 직접 써야 한다면 실제로는 한 건도 고치지 않게 됩니다. 결과 화면에도 "이 책이 아닌가요?" 버튼을 두어 신고를 쌓습니다. 개인 도구에서는 이 버튼 하나가 피드백 경로의 전부입니다.

### 검증 방법

`src/test/resources/bib/golden-pairs.tsv`에 한국어 쌍 200건 정도를 손으로 판정해 둡니다(같은 저작 / 다른 저작 / 각색). **이 파일이 "같은 책"의 실질적인 명세이고 코드는 그 구현입니다.** 정밀도 0.99 이상, 재현율 0.90 이상을 통과 기준으로 삼고, `norm(norm(x)) == norm(x)`와 `sameWork(a,b) == sameWork(b,a)` 같은 성질도 함께 검사합니다.

## 8. 색인 적재 파이프라인

### 전체 흐름

```
정보나루 벌크 파일 ─┐
ISBN 서지정보 API ─┼→ [원본 아카이브 R2] → [스테이징 테이블] → [정규화·동일성 판별]
도서관 정보 서비스 ─┤                                                    ↓
전국도서관표준데이터┘                                        [DB 정규화 원본] → [search_doc_vN] → 뷰 전환
```

핵심 원칙은 **내려받은 것은 무조건 먼저 아카이브에 그대로 저장한다**는 것입니다. 파싱에 실패하더라도 원본은 남아 있어야 나중에 파서만 고쳐서 다시 처리할 수 있습니다.

### 배치 구성

| 잡 | 주기 | 내용 |
|---|---|---|
| `library-master-sync` | 월 1회 | 도서관 정보 제공 서비스와 전국도서관표준데이터를 받아 `library`를 갱신합니다. |
| `holdings-ingest` | 월 1회 | 1,604개관의 장서 벌크 파일을 순회하며 스테이징에 적재합니다. 도서관 단위로 `ingest_run`을 남기고, 한 곳이 실패해도 다음 도서관으로 넘어갑니다. |
| `seoji-ingest` | 주 1회 | ISBN 서지정보 API를 **발행일 구간으로 나눠** 받아옵니다. |
| `reindex` | 월 1회 (적재 후) | 정규화와 동일성 판별을 수행하고 `search_doc_vN`을 새로 만든 뒤 뷰를 전환합니다. |
| `link-health-check` | 주 1회 | 리다이렉트 템플릿의 유효성을 점검합니다 (11절). |

**Spring Batch는 쓰지 않습니다.** Spring Batch의 잡 저장소가 `ingest_run`과 기능이 겹쳐 같은 상태를 두 곳에서 관리하게 되고, 청크 모델이 아래의 `COPY` 방식과 잘 맞지 않습니다. 평범한 `@Component` 어댑터와 40줄짜리 오케스트레이터로 충분합니다. 익숙한 프레임워크를 쓰는 것보다 이 경우에는 단순한 편이 낫습니다.

### 적재는 반드시 COPY로 합니다

이것이 적재 성능에서 가장 중요한 결정입니다. JDBC로 한 행씩 `INSERT`하면 수백만 행에 두 시간이 걸리지만, `COPY`로 흘려보내면 1~2분에 끝납니다.

```java
conn.unwrap(PGConnection.class).getCopyAPI().copyIn(sql, reader);  // PipedReader로 변환 결과를 스트리밍
```

스테이징 테이블은 실행마다 버리는 임시 데이터이므로 `UNLOGGED`로 만들어 WAL 기록을 건너뜁니다. 대량 적재 구간에서는 세션 설정으로 `synchronous_commit = off`, `maintenance_work_mem = 512MB`를 적용하고, 도서관 하나가 끝날 때마다 `ANALYZE`를 실행합니다.

### 멱등성은 파일 해시로 확보합니다

```sql
UNIQUE (source_code, coalesce(scope_key,''), input_sha256)
```

`ingest_run`에 이 제약 하나를 두면 **같은 파일을 다시 적재하는 것이 자동으로 건너뛰기가 됩니다.** 파일을 다시 받는 일은 반드시 생기므로 이 제약이 실질적인 안전장치가 됩니다.

### 실패 격리

**트랜잭션은 (소스, 도서관) 하나당 하나입니다.** 실패한 도서관만 되돌아가고, 반복문이 예외를 잡아 `FAILED`로 기록한 뒤 다음 도서관으로 넘어갑니다. 도서관을 가로지르는 트랜잭션은 어디에도 두지 않습니다. 전체 실행은 `PARTIAL`로 끝나고, 실패한 대상만 골라 재실행하는 진입점을 처음부터 만들어 둡니다. 1,604개관 중 30곳이 실패했을 때 전체를 다시 돌리는 것은 현실적이지 않습니다.

소장 데이터는 **절대 물리적으로 삭제하지 않고** `is_active = false`로 표시합니다. "원래 없었다"와 "사라졌다"를 구분해야 아래의 감지가 성립합니다.

### 데이터가 사라진 것을 감지하는 세 가지 장치

실패 양상이 다르므로 장치도 따로 둡니다. 세 번째가 특히 중요한데, 앞의 둘은 배치가 돌아야만 작동하기 때문입니다.

1. **파일이 잘렸거나 깨진 경우**: 읽은 행 수가 직전 성공 실행의 70% 미만이면 실패로 처리하고 되돌립니다. 진행하려면 명시적으로 강제 옵션을 줘야 합니다.
2. **파일은 정상인데 대량으로 사라진 경우**: 비활성으로 바뀌는 행이 기존 활성 행의 20%를 넘으면 실패로 처리하고 되돌립니다.
3. **도서관이 정보나루에서 아예 빠진 경우**: 배치가 돌지 않으므로 위 둘로는 잡히지 않습니다. 별도의 신선도 감시를 둡니다.

```sql
SELECT lib_code, max(finished_at) AS last_ok
FROM library l JOIN ingest_run r ON r.target_key = l.lib_code AND r.status = 'succeeded'
GROUP BY lib_code HAVING max(finished_at) < now() - interval '45 days';
```

45일이 지나면 경고하고, 60일이 지나면 화면에 "데이터 기준: 2026-06 (오래됨)"을 표시합니다. **화면에는 언제나 도서관별 기준 시점을 표시합니다.** 사용자가 "미소장"을 보고 "확실히 없다"로 읽을지 "3개월 전 기준이다"로 읽을지가 이 표시 하나에 달려 있습니다.

### 서지 적재는 발행일 구간으로 훑습니다

**ISBN을 하나씩 조회하면 절대 끝나지 않습니다.** 350만 건을 1일 한도 안에서 하나씩 부르면 몇 년이 걸립니다. `SearchApi.do`가 `start_publish_date`와 `end_publish_date`, `page_no`, `page_size`를 지원하므로, **1990년 1월부터 현재까지 월 단위 구간으로 나눠 `page_size=500`으로 훑습니다.** 한국의 연간 ISBN 발행량을 고려하면 전체가 약 4,000회 요청으로 끝나고, 하루 한도 안에서 며칠이면 완료됩니다. 이후에는 순수한 로컬 조인이 되어 **검색 시점의 API 호출이 0회**가 됩니다.

### 초기 적재를 감당하는 방법

1,604개관을 한 번에 처리하려 들지 않습니다. 도서관 목록을 시도 순으로 정렬해 두고, `ingest_run`을 진행 표시로 삼아 중단된 지점부터 이어갑니다. GitHub Actions의 6시간 제한에 걸리면 다음 실행이 남은 곳부터 이어받습니다.

스테이징에서 색인까지는 도서관 단위가 아니라 **전체를 모은 뒤 한 번에** 처리합니다. 소장 색인이 책 단위 배열이라 도서관 하나만 갱신하려면 많은 행을 건드려야 하기 때문이고, 월 1회 전량 재생성이 훨씬 단순하고 안전합니다.

### 색인 검증 없이는 전환하지 않습니다

```
1. search_doc_v2 생성 및 적재
2. 검증:
     문서 수가 예상치의 ±5% 이내인가
     고정 질의가 통과하는가:  "해리포터" → 1건 이상
                              "9788983920775" → 정확히 한 저작으로 해석
                              "코스모스" → 상위 3건 안에 칼 세이건
   실패하면 새 테이블을 버리고 기존 뷰를 그대로 둡니다. 경고만 남깁니다.
3. 통과하면 뷰 전환
4. 이전 세대는 두 개까지만 남기고 정리
```

**검증하지 않은 색인은 절대 전환하지 않습니다.** 자동 배치가 조용히 망가진 색인으로 갈아 끼우는 것이 이 구조에서 가장 위험한 실패입니다.

## 9. 소스 어댑터 인터페이스

소스 추가와 제거가 설정 변경 수준이 되도록, 어댑터는 **본 테이블에 직접 쓰지 않습니다.** 어댑터는 소스 형태의 레코드를 내보내기만 하고, 정규화와 저장은 파이프라인이 담당합니다. 이 불변식 하나가 소스 교체 가능성의 전부입니다.

```java
public record SourceRecord(
    SourceRecordKind kind,           // LIBRARY | BIB | HOLDING | OPAC_TEMPLATE
    SourceRef ref,                   // (소스 코드, 소스 레코드 ID)
    String scopeKey,                 // HOLDING이면 도서관부호, 그 외에는 null
    Map<String,String> fields,       // 소스 고유 필드명 그대로
    String rawPayload                // 원본 한 줄. 사후 추적용
) {}

public record IngestUnit(            // 재시도 가능한 최소 단위
    String sourceCode, String scopeKey, String sourceVersion,
    IngestMode mode, URI input, String inputSha256
) {}

public record SourceCapabilities(
    boolean bulkSnapshot,            // true면 파이프라인이 비활성 처리를 수행
    boolean incremental,
    int     dailyCallBudget,         // 0이면 파일 기반
    Duration minRequestInterval,
    int     trustScore               // 0~100. 소스 간 필드 충돌을 해소하는 기준
) {}

public interface SourceAdapter {
    String code();
    Set<SourceRecordKind> produces();
    SourceCapabilities capabilities();
    List<IngestUnit> discover(DiscoveryContext ctx);      // 지금 처리할 일감 목록
    void fetch(IngestUnit unit, RecordSink sink);         // 처음부터 다시 실행 가능해야 함
}

public interface RecordSink {
    void accept(SourceRecord r);
    void reject(String rawLine, String reasonCode, String detail);  // 예외 대신 거부 기록
    void progress(long rowsRead);
}
```

`reject`가 예외와 분리되어 있는 것이 의도적입니다. 변환할 수 없는 레코드(ISBN이 없는 자료 등)는 건수만 세어 남기고 넘어갑니다. 한 줄의 형식이 이상하다고 해서 그 도서관 전체의 적재가 중단되면 안 됩니다.

기반 클래스 둘로 앞으로 붙일 모든 소스를 덮습니다.

- `DelimitedFileSourceAdapter`: 문자 인코딩 판별(UTF-8 우선, 실패 시 CP949), BOM 제거, 따옴표 처리, 행 번호 추적, SHA-256 계산, **헤더 지문 검사**를 제공합니다.
- `HttpApiSourceAdapter`: 호출 한도에 따른 토큰 버킷, **재시작해도 유지되는 일일 한도 원장**, 5xx와 타임아웃에 대한 지수 후퇴 재시도, 응답 캐시를 제공합니다.

**헤더 지문 검사를 반드시 넣습니다.** CSV 컬럼 구성이 소리 없이 바뀌면 컬럼이 밀려서 전혀 다른 데이터가 적재되는데, 나중에는 사실상 발견할 수 없습니다. 기대한 헤더와 다르면 **실행을 실패시킵니다.**

설정으로 켜고 끄는 구조는 `@ConditionalOnProperty`로 처리합니다. 비활성 소스는 빈 자체가 만들어지지 않아 `discover()`가 호출되지 않습니다.

```yaml
wimb:
  sources:
    DATA4LIBRARY_BULK: { enabled: true,  trustScore: 60 }
    SEOJI_API:         { enabled: true,  trustScore: 90, dailyCallBudget: 9000,
                         backfill: { from: 1990-01, to: now, pageSize: 500 } }
    DATA4LIBRARY_API:  { enabled: true,  trustScore: 55, dailyCallBudget: 25000 }  # 30,000 한도에 여유
    NLK_LIB_MASTER:    { enabled: true,  trustScore: 95 }
    LIB_STD_DATA:      { enabled: true,  trustScore: 70 }
    YES24_API:         { enabled: false, trustScore: 40 }
    KOLISNET:          { enabled: false }
```

**필드 단위 출처 관리**가 "소스 추가"를 아무 일도 아닌 것으로 만듭니다.

```sql
CREATE TABLE bib_field_provenance (
  book_id INTEGER, field_name TEXT, source_code TEXT,
  value TEXT, trust INT, observed_at TIMESTAMPTZ,
  PRIMARY KEY (book_id, field_name, source_code)
);
-- 본 테이블의 값 = 신뢰도가 가장 높은 비어 있지 않은 값
```

나중에 붙일 소스가 어떻게 들어오는지는 아래와 같고, **어느 경우에도 스키마 변경이 필요하지 않습니다.**

| 소스 | 내보내는 것 | 필요한 것 |
|---|---|---|
| 예스24 | `BIB` (표지, 책소개, 목차) | 신뢰도 40이므로 서지정보 API가 비워 둔 필드만 채웁니다. 설정 변경뿐입니다. |
| KOLIS-NET | `LIBRARY`, `BIB`, `HOLDING` | 자체 도서관 ID를 `library_source_link`에 도서관부호와 연결합니다. |
| RISS | `HOLDING` | **공개 API가 없어 크롤링이 됩니다. 권하지 않습니다.** 대학도서관은 소속이 없으면 대출도 되지 않아 실사용 가치가 낮습니다. |
| 카카오 책 검색 | `BIB` (표지 대체) | 신뢰도 30. 설정 변경뿐입니다. |

## 10. 검색 화면

### 한 권 검색

결과는 세 부분으로 구성합니다.

1. **책 정보**: 제목, 저자, 출판사, 발행일, 정가.
2. **소장 도서관**: 선택한 도서관 중 소장한 곳만 표시합니다. **대출 상태는 표시하지 않고**, 대신 `as_of_date`를 "소장 정보 기준 2026년 8월 1일"처럼 명시합니다. 각 항목에는 해당 도서관의 도서 페이지 링크를 답니다. 아직 소장 데이터를 적재하지 못한 도서관(`holdings_state <> 'indexed'`)을 선택했다면 "소장 정보 준비 중"으로 따로 묶어 표시합니다. 조용히 빠뜨리면 "없다"는 뜻으로 잘못 읽힙니다.
3. **그 외 경로**: 서점과 전자책 서비스의 검색 페이지 링크(4단계).

### 여러 권 동시 확인

**입력**은 큰 텍스트 영역 하나로 받고 줄 단위로 해석합니다. 별도의 입력 방식을 고르게 하지 않고 자동으로 판별하며, 50줄을 상한으로 두고 그 사실을 안내 문구에 적습니다.

```
줄마다:
  P1  앞머리의 번호와 기호를 제거합니다:  ^\s*[-*•·]?\s*(\d+[.)])?\s*
  P2  서점 URL이면 경로에서 ISBN을 추출합니다.
  P3  영숫자만 남겨 13자리(978/979)면 ISBN13, 10자리면 체크디지트 검증 후 변환합니다.
  P4  그 외에는 제목으로 봅니다.
  P5  제목으로 결과가 0건이면 마지막 " - ", " / ", ", "에서 나눠 (제목, 저자)로 재시도합니다.
  P6  정규화 결과가 같은 줄은 합치되, 원본 문구는 화면 표시용으로 남깁니다.
```

**어떻게 해석했는지를 항상 되돌려 보여줍니다.** `1. 코스모스 - 칼 세이건` → `제목: 코스모스, 저자: 칼 세이건 (제목·저자 분리)`. 사용자가 왜 이 결과가 나왔는지 알 수 있어야 스스로 고칠 수 있습니다.

상태는 셋입니다. **확정**은 후보가 하나이거나 1위 점수가 2위의 두 배 이상인 경우이고, 조용한 "다른 책인가요?" 링크만 답니다. **모호**는 그 줄만 후보 칩 다섯 개(제목 · 저자 · 출판연도 · "n개 관 소장")로 펼쳐 고르게 합니다. **결과 없음**은 줄을 직접 고칠 수 있게 하고, 정보나루에 직접 조회하는 버튼을 하나 둡니다(서버에서 호출 간격을 제어하고 결과를 7일 이상 캐시합니다).

후보 점수에는 **"내가 선택한 도서관이 소장하고 있으면 1.5배"** 규칙을 넣습니다. 일반적인 책 검색이 할 수 없는 보정이고, 동명이서 문제를 대부분 저절로 해결합니다. 30개 관 중 28곳이 가진 「코스모스」가 아무 데도 없는 동명의 시집을 이깁니다.

### 소장 상태를 여섯 가지로 구분합니다

"소장/미소장" 두 가지로는 부족하고, 특히 각색본을 소장으로 세면 헛걸음이 생깁니다.

| 상태 | 의미 | 표시 | 집계 포함 |
|---|---|---|---|
| `FULL` | 그 저작의 판본을 소장 | ● | 포함 |
| `OTHER_EDITION` | 다른 판(개정판 등)을 소장 | ● + 배지 | 포함 |
| `OTHER_FORM` | 큰글자책·점자·오디오북만 소장 | ◐ | 제외 (토글) |
| `SERIES_PARTIAL` | 여러 권 중 일부만 소장 | ◐ "3/5권" | 제외 (토글) |
| `DERIVATIVE_ONLY` | 만화판·청소년판만 소장 | ◐ + 명시적 문구 | **절대 제외** |
| `NONE` | 미소장 | ○ | 제외 |

`DERIVATIVE_ONLY`는 반드시 이름을 붙여 표시하고 절대 조용히 집계에 넣지 않습니다. 7절의 각색 표기 구분이 화면에서 값을 하는 지점이 여기입니다.

### 결과 표시

도서관 × 책 행렬을 기본 화면으로 두지 않습니다. 20개 관에 30권이면 600칸이라 좁은 화면에서 읽을 수 없습니다. 실제 행동은 "한 곳을 골라서 가는 것"이므로 기본은 **도서관 순위 목록**입니다.

```
├ 성남시중원도서관        30권 중 18권 소장   [도서관 페이지]
│   소장: 미움받을 용기 · 사피엔스 · 총 균 쇠 · … (18)
│   없음: 물고기는 존재하지 않는다 · … (12)
├ 분당도서관              30권 중 15권 소장
```

여기에 **"한 곳에서 다 빌리기" 패널**을 더합니다. 이것이 "한 번 방문해서 여러 권을 빌린다"는 실제 행동에 가장 직접적으로 답하는 출력이고, 탐욕 알고리즘 15줄이면 됩니다.

```
1개 관:  성남시중원도서관              24/30
2개 관:  + 분당도서관                  28/30
4개 관:  + 판교도서관 + 수정도서관     30/30
남는 책: 「…」 2권은 선택한 도서관에 없습니다
```

집합 덮개 문제의 최적해는 계산이 어렵지만, 도서관 20곳 규모에서는 탐욕 방식으로 충분하고 차이도 거의 없습니다.

보조 화면인 **책 기준 목록**에서는 어디에도 없는 책을 맨 위에 모읍니다. 서점이나 전자책으로 넘어가야 하는 대상이므로 가장 먼저 알아야 합니다.

행렬 표는 넓은 화면에서만 세 번째 탭으로 제공합니다. 책이 행, 도서관이 열이고 첫 열을 고정하며, 열은 소장 권수 내림차순으로 정렬해 가장 좋은 도서관이 왼쪽에 오게 합니다. 칸은 **색만으로 구분하지 않고 모양을 함께 씁니다.** 가로 스크롤은 표를 감싼 컨테이너 안에서만 일어나게 합니다. 좁은 화면에서는 행렬을 아예 그리지 않습니다.

**"결과 복사" 버튼**을 답니다. 메모 앱에 붙여 넣고 도서관에 가져가게 되는 것이 실제 사용 흐름이므로, 비용에 비해 쓸모가 큽니다.

## 11. 리다이렉트 URL 생성과 링크 유효성 점검

### 생성 방식

1,604개 도서관이 저마다 다른 OPAC을 쓰므로 전부에 대해 도서 상세 링크를 만들 수는 없습니다. 그래서 **템플릿을 코드가 아니라 운영 데이터로 두고**, 단계적으로 낮아지는 폴백을 둡니다.

| 우선순위 | `template_kind` | 예시 | 도달 지점 |
|---|---|---|---|
| 1 | `isbn_detail` | `https://lib.example.kr/detail?isbn={isbn13}` | 그 책의 상세 페이지 |
| 2 | `isbn_search` | `https://lib.example.kr/search?q={isbn13}` | ISBN 검색 결과 |
| 3 | `title_search` | `https://lib.example.kr/search?q={title}` | 제목 검색 결과 |
| 4 | `homepage` | 표준데이터의 홈페이지주소 | 도서관 첫 화면 |

4번은 전국도서관표준데이터에 홈페이지주소가 있으므로 **항상 존재합니다.** 즉 링크가 없어서 아무 데도 못 가는 경우는 발생하지 않습니다. 다만 어느 단계의 링크인지 화면에 정직하게 표시합니다. "도서관 홈페이지로 이동"과 "검색 결과 바로가기"를 구분하지 않고 조용히 강등하면, 사용자는 검색 결과 자체가 틀렸다고 생각하게 됩니다.

템플릿은 도서관마다 따로 만들지 않고 **벤더 계열별로 한 번 만든 뒤 도서관별 변수만 다르게 둡니다.** 국내 공공도서관 OPAC은 소수의 솔루션에 몰려 있어서, 계열 5~10개가 상당수를 덮습니다.

```sql
CREATE TABLE opac_template (
  family_code       TEXT PRIMARY KEY,
  url_pattern       TEXT NOT NULL,   -- '{base}/search?searchKeyword={q}'
  query_kind        TEXT NOT NULL,   -- ISBN | TITLE | TITLE_AUTHOR
  encoding          TEXT DEFAULT 'UTF-8',
  no_result_markers TEXT[],          -- '검색된 자료가 없습니다', '총 0건'
  ok_markers        TEXT[]
);
```

**문자 인코딩을 템플릿 속성으로 둔 것이 중요합니다.** 국내 OPAC 중에는 한글 질의를 EUC-KR로 퍼센트 인코딩해야 하는 곳이 아직 있습니다. UTF-8로 보내면 HTTP 200이 돌아오면서 결과만 0건이 되는데, 이것은 조용히 실패하는 가장 나쁜 형태입니다. 계열마다 알려진 ISBN으로 검사하는 고정 테스트를 하나씩 둡니다.

URL은 **서버에서 생성합니다.** 고칠 곳이 한 군데로 모이고, 아래의 클릭 훅을 둘 수 있습니다.

`GET /go/{libCode}?work={workId}`로 302 전달을 합니다. 이렇게 하면 어느 템플릿이 실제로 쓰이는지 알 수 있고, 클릭 시점의 최신 상태로 폴백 단계를 다시 계산할 수 있습니다.

1,604곳을 전부 손으로 만들려 하면 이 프로젝트는 끝나지 않습니다. **자주 가는 도서관부터 채우고 나머지는 폴백에 맡깁니다.** 템플릿 파일은 저장소에 CSV로 두고 파일 어댑터로 적재해서, 템플릿 변경이 검토 가능한 차이로 남게 합니다. 크롤링으로 템플릿을 자동 발견하려는 시도는 하지 않습니다. 주말을 통째로 쓰고 쓸 만한 결과가 나오지 않습니다.

### 링크 점검

**도서관 서버에 부담을 주지 않는 것을 최우선으로 합니다.**

- **점검 대상을 좁힙니다.** 전수를 확인하지 않고, 최근 90일 안에 실제로 클릭된 도서관과 최근에 실패한 도서관만 봅니다. 1,604곳이 아니라 수십 곳이 되므로 부담 문제가 대부분 사라집니다.
- 도서관 한 곳당 주 1회를 넘지 않고, 같은 호스트에 동시 요청은 1개, 전체 6회/분을 넘지 않게 간격을 흩뜨립니다.
- **점검 시간대를 평일 오후(13~17시)로 잡습니다.** 새벽에 돌리는 것이 예의처럼 보이지만, 국내 공공기관 사이트는 야간에 점검 작업을 하는 경우가 많아 새벽 점검은 멀쩡한 링크를 고장으로 잘못 판정합니다. 도서관당 주 1회 요청은 낮 시간대 트래픽에서 식별되지도 않는 양입니다.
- `robots.txt`를 확인하고 거부된 경로는 점검하지 않습니다. `User-Agent`에 연락 가능한 주소를 밝힙니다.
- **2단계로 나눠 확인합니다.**
  - 1단계(주 1회, 가벼움): `HEAD {base}`. 거부하면 `Range: bytes=0-0`을 붙인 `GET`으로 대체합니다. DNS와 TLS, 호스트 소멸을 잡습니다.
  - 2단계(월 1회): **그 도서관이 확실히 소장한 책으로 질의합니다.** 우리가 소장 데이터를 가지고 있기 때문에 가능한 방법입니다.

```sql
SELECT isbn13 FROM holding h JOIN book b ON b.book_id = h.book_id
WHERE h.lib_code = :lib AND h.is_active
ORDER BY h.book_id LIMIT 1;   -- 고정된 선택이라 시점 간 비교가 가능합니다
```

응답 본문에 `no_result_markers`가 없고 `ok_markers`나 제목 앞 네 글자가 있는지 확인합니다. **국내 OPAC은 결과가 없어도 대부분 200을 반환하므로 상태 코드만 보는 점검은 아무것도 검증하지 못합니다.**

- 연결 3초, 읽기 5초, 전달 3회, 본문 256KB로 제한합니다. 외부 도메인으로 넘어가면 따라가지 않되 **`Location` 값을 새 `base_url` 후보로 제안합니다.** 대개 그것이 실제로 일어난 일입니다.
- **연속 3회 실패하면 한 단계 낮은 폴백으로 강등하고** 관리 목록에 올립니다. 재시도 간격은 7일, 14일, 30일로 늘리고 그 이상 자주 두드리지 않습니다.
- 자바스크립트로만 동작하거나 POST만 받는 OPAC은 2단계 검증이 불가능합니다. **헤드리스 브라우저를 만들지 않습니다.** `UNVERIFIABLE`로 표시해 링크는 살려 두고, 화면에 "링크가 안 돼요" 버튼을 두어 신고를 받습니다. 개인 도구에서는 이 버튼 하나가 브라우저 농장보다 값집니다.

## 12. 정보나루 인증키 신청과 한도 상향

### 절차

1. `data4library.kr`에 회원으로 가입합니다.
2. **데이터 활용** 메뉴에서 인증키 이용신청을 합니다. 자료의 사용 목적과 용도를 기재해야 하며, 승인까지 기다려야 합니다. 개인 프로젝트라는 점과 소장 정보 조회 용도라는 점을 적으면 됩니다.
3. 승인 후 **마이페이지 > 인증키 관리**에서 `서버IP` 항목에 호출이 일어날 서버의 IP 주소를 입력합니다. 이 등록으로 **1일 호출 한도가 500건에서 30,000건으로 확대됩니다.**

### 반드시 유의할 점

**30,000건이 상한이며, 무제한은 없습니다.** 2023-11-20부터 무제한 호출이 중단되었습니다. 검색할 때마다 API를 부르는 설계는 애초에 불가능하며, 이 계획이 벌크 적재와 자체 색인을 전제로 하는 이유가 여기에 있습니다.

**IP 등록에는 고정 IP가 필요한데, GitHub Actions 러너의 IP는 고정되지 않습니다.** 배치를 GitHub Actions에서 돌리면 등록한 IP와 실제 호출 IP가 달라져서 한도 상향의 효과를 받지 못하고 1일 500건 제한이 적용됩니다. 따라서 **정보나루 API를 호출하는 배치는 Fly.io에 전용 IPv4(월 약 2달러)를 붙인 머신에서 실행하고**, 그 IP를 등록해야 합니다. GitHub Actions는 그 머신을 깨우는 예약 트리거로만 씁니다.

벌크 파일 내려받기가 API 호출 한도에 포함되는지는 확인하지 못했으므로, 0단계에서 실제로 확인합니다. 포함되지 않는다면 벌크 다운로드만 GitHub Actions에서 처리하는 구성도 가능합니다.

### 준비물 정리

- 고정 IP 주소 1개 (Fly.io 전용 IPv4)
- 서비스 설명과 사용 목적 문구
- 국립중앙도서관 ISBN 서지정보 API의 `cert_key`는 별도로 신청해야 하므로 함께 진행합니다.

## 14. 검증 방법

단계마다 아래 순서로 직접 확인합니다.

**적재 검증** — 배치를 로컬에서 도서관 3곳으로 한정해 실행하고, `ingest_run`에 성공 이력이 남는지, 같은 배치를 두 번 돌렸을 때 결과가 같은지(멱등성) 확인합니다. 일부러 잘못된 파일을 하나 섞어서 그 도서관만 실패하고 나머지는 정상 적재되는지 확인합니다.

**정규화 검증** — 7절의 예시 표를 단위 테스트로 고정합니다. 규칙을 바꿀 때마다 이 테스트가 회귀를 잡습니다. 그다음 실제 데이터에서 무작위 100건을 뽑아 사람이 확인합니다.

**검색 검증** — 본인이 실제로 찾을 책 20권 정도로 고정 질의 목록을 만들어 두고, 색인을 다시 만들 때마다 그 20권이 전부 검색되는지 확인합니다. 띄어쓰기를 바꾼 질의, 부제를 뺀 질의, 오타가 있는 질의를 포함시킵니다.

**재색인 검증** — `search_doc_v2`를 만들고 뷰를 전환하는 동안 프론트에서 계속 검색을 실행해 오류가 나지 않는지 확인합니다.

**화면 검증** — 실제 휴대폰으로 3단계 화면을 열어서 도서관 20곳, 책 30권 조건으로 읽히는지 확인합니다. 이 확인은 개발자 도구의 반응형 모드가 아니라 실제 기기로 합니다.

## 15. `CLAUDE.md`에 담을 내용 제안

계획이 확정되면 아래 내용을 `CLAUDE.md`로 만들겠습니다. 이후 세션에서 같은 실수를 반복하지 않게 하는 것이 목적이므로, 일반론이 아니라 **이 프로젝트에서만 성립하는 제약**을 위주로 적습니다.

1. **사용할 수 없는 소스 목록과 그 이유.** 알라딘(2026-10-30 종료), 네이버 책(2026-07-31 종료), 교보문고(공식 API 없음). 학습 데이터를 근거로 이것들을 다시 제안하지 말 것.
2. **대출 상태는 어떤 경우에도 표시하지 않는다.** `bookExist`를 사용하지 않는다. 소장 여부까지만 보여주고 대출 가능 여부는 도서관 페이지로 넘긴다. 이것은 성능 문제가 아니라 제품 결정이다. 벌크 데이터에 대출 관련 필드가 함께 들어 있으므로 스테이징 테이블에서 눈에 띄겠지만, 화면에 내보내지 않는다.
3. **정보나루 API 한도는 1일 30,000건이 상한이다.** 검색 시점에 외부 API를 호출하는 코드를 작성하지 말 것. 그리고 `libSrchByBook`은 ISBN 하나로 소장 도서관 전체를 돌려주므로, **(책 × 도서관)으로 호출하지 말 것.** 30권이면 30회이지 600회가 아니다.
4. **서지정보 API를 ISBN 하나씩 조회하지 말 것.** 발행일 구간으로 훑는다.
5. **`short_id`와 `work_id`는 절대 재사용하거나 변경하지 않는다.** 둘 다 공유 URL에 들어가므로 재색인 때 번호가 바뀌면 공유된 링크가 전부 조용히 깨진다. `work_id`는 최빈값 승계와 별칭 표로 유지한다.
6. **판본 표기와 각색 표기를 혼동하지 말 것.** `개정판`, `양장본`은 제거해서 묶고, `청소년판`, `만화`, `큰글자책`은 병합 거부의 근거로 쓴다. 이 두 목록을 섞는 것이 오병합의 가장 큰 원인이다.
7. **정규화 함수는 한 곳에만 둔다.** 적재와 질의가 같은 함수를 호출해야 한다.
8. **CSV 헤더 지문이 다르면 실행을 실패시킨다.** 컬럼이 밀린 채 적재되면 나중에 발견할 수 없다. 인코딩은 UTF-8을 먼저 시도하고 CP949로 대체한다.
9. 어댑터는 본 테이블에 직접 쓰지 않는다. 소스 고유 필드가 도메인 모델이나 색인 스키마에 나타나면 안 된다.
10. **전국도서관표준데이터에는 작은도서관과 대학·전문도서관이 섞여 있다.** 선택 화면을 만들 때 `도서관유형`으로 공공도서관만 걸러야 목록이 쓸 만해진다.
11. **화면에 출처를 표시한다.** "출처: 도서관 정보나루 · 국립중앙도서관"과 도서관별 데이터 기준 시점. 이용 조건상의 의무이면서, "미소장"을 믿게 만드는 신뢰 표시이기도 하다.
12. API 키는 `.env`로 관리하고 저장소에 커밋하지 않는다. `.env.example`에 키 이름만 둔다.
13. 링크 점검 배치의 동시 요청 상한과 요청 간격을 임의로 올리지 않는다.
14. 저장은 `timestamptz`로 UTC, 표시는 전부 `Asia/Seoul`. 월별 스냅숏 경계는 한국 시각 기준 개념이다.
15. 개발 명령어(빌드, 테스트, 배치 로컬 실행)와 디렉터리 구조 요약.

## 16. 남아 있는 위험

정직하게 적어 둡니다.

**가장 큰 위험은 0단계에서 확인할 벌크 다운로드의 자동화 가능성입니다.** 1,604개관의 파일을 화면에서 하나씩 눌러 받아야 하는 구조라면 이 계획의 적재 부분을 다시 설계해야 합니다. 그래서 0단계를 별도 단계로 분리했습니다. 자동화가 불가능하다면 정보나루의 다운로드 화면을 크롤링하는 대신, **자주 가는 도서관부터 손으로 받아 `inbox/`에 넣으면 배치가 처리하는 구조**로 전환합니다. 월 30회 내려받기는 견딜 만하지만 로그인 화면이 바뀔 때마다 깨지는 크롤러는 견딜 수 없습니다.

**두 번째는 전국도서관표준데이터와 도서관부호의 대조 정확도입니다.** 도서관명 표기가 자료마다 달라서(`○○시립도서관` 대 `○○시 ○○도서관`) 자동 대조가 100%가 되지 않습니다. 단계적으로 시도합니다.

```
M1  (시도, 시군구, 정규화 도서관명) 완전 일치
M2  도로명 + 건물번호 + 도서관명 앞 4글자
M3  직선거리 150m 이내 && 이름 유사도 0.6 이상
그 외 → 미대조
```

모든 연결은 `library_source_link(source_code, source_key, lib_code, match_method, score, confirmed)`에 남기고, **`confirmed = true`인 행은 재실행해도 덮어쓰지 않습니다.** 자주 가는 도서관 몇십 곳만 직접 확인해 두면 실제 사용에는 지장이 없고, 나머지는 미대조로 남겨도 이름 검색과 지역 계층에서는 정상적으로 찾힙니다. 다만 위경도가 없어 "내 주변"에는 나오지 않으므로, 미대조 목록을 관리 화면에서 확인하고 채울 수 있게 합니다.

**세 번째는 규모 추정의 불확실성입니다.** 3절의 복본율 1.3과 ISBN 보유율 80%는 가정이며, 실측과 크게 다르면 저장 용량과 비용이 달라집니다. 다만 소장 색인을 책 단위 배열로 접는 설계 덕분에 추정이 두 배 틀려도 800MB 수준이므로, 이 위험이 설계를 뒤집지는 않습니다.

**네 번째는 PGroonga에 대한 의존입니다.** Neon의 `pg_search`가 6개월 예고 후 제거되는 것을 보면 관리형 서비스의 확장 지원은 영구적이지 않습니다. 그래서 대체 경로를 미리 정해 둡니다. 정규화한 `search_text`에서 우리가 직접 2글자 조각을 만들어 `simple` 설정의 `tsvector`에 넣는 방식입니다.

```java
static String bigrams(String key) {          // key는 이미 공백이 제거된 정규화 문자열
    var sb = new StringBuilder();
    for (int i = 0; i + 1 < key.length(); i++) sb.append(key, i, i + 2).append(' ');
    return key.length() == 1 ? key : sb.toString();
}
// "해리포터" → "해리 리포 포터".  질의 "포터"도 걸리고, "해리포터"는 세 조각 모두를 요구해 정확합니다.
```

확장도, 별도 프로세스도 필요 없습니다. PGroonga를 쓸 수 없게 되면 색인 정의와 질의 생성부만 바꾸면 되고 재적재는 필요하지 않습니다.

**다섯 번째는 정보나루 호출 IP 문제입니다.** 12절에 적었듯 GitHub Actions의 IP는 고정되지 않아서, 여기서 API를 호출하면 한도 상향이 적용되지 않고 1일 500건으로 떨어집니다. 문제는 이것이 조용히 일어난다는 점입니다. 배치가 절반쯤 돌다가 한도에 걸려 멈추는 형태로 나타나므로, 고정 IP를 쓰는 구성을 처음부터 잡거나 500건 기준으로 설계해야 합니다.
