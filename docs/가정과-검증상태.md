# 가정과 검증 상태

이 저장소의 코드가 어디까지 검증되었고 어디부터 추측인지 적어 둡니다.

**2026-09-05 갱신:** 정보나루 Open API Manual (v20260210) 을 확보해 3번 항목이 대부분
사실로 바뀌었습니다. 아래 "매뉴얼로 밝혀진 것" 을 보세요.

## 1. 실제로 실행해 검증한 것

| 대상 | 어떻게 |
|---|---|
| DB 스키마 | PostgreSQL 16 에 실제로 적용하고, `short_id` 불변 트리거·ISBN 제약·멱등성 제약·색인 전환의 원자성을 각각 동작시켜 확인 |

| 로직 전반 | 테스트 96개 (백엔드) + 22개 (프론트) |

## 2. 매뉴얼로 밝혀진 것 (v20260210)

문서에 근거가 있으므로 추측이 아닙니다. 다만 **실제 응답을 받아 본 것은 아닙니다.**

### 계획이 바뀐 것

**`libSrchByBook` 의 `region` 은 필수입니다.** 전국을 한 번에 받는 방법이 없습니다.
소장 조회는 선택한 도서관들이 걸친 시도 수만큼 호출이 곱해집니다.
30권 × 판본 3개 × 시도 2곳이면 180회입니다.

**`libSrch` 가 위도와 경도를 줍니다.** 계획서는 위경도를 얻으려고 공공데이터포털의
전국도서관표준데이터를 받아 이름과 주소로 대조하는 단계를 두었고, 표준데이터에 도서관부호가
없어 그 대조를 **계획 전체에서 가장 큰 위험**으로 꼽았습니다. 정보나루가 코드와 위경도를
함께 주므로 **그 단계가 통째로 필요 없어집니다.**

**정보나루 하나로 1차 범위가 채워집니다.**

| 필요한 것 | 어디서 |
|---|---|
| 도서관 마스터 (코드·주소·위경도·홈페이지·휴관일·운영시간) | `libSrch` |
| 서지 (제목·저자·출판사·ISBN·세트ISBN·표지·대출건수) | `srchBooks` |
| 소장 도서관 | `libSrchByBook` |

국립중앙도서관 서지정보 API 와 공공데이터포털은 **서지 품질 보강용으로 나중에** 붙이면 됩니다.
1차를 시작하는 데 필요하지 않습니다.

### 제 가정이 틀렸던 것

- **부가기호는 `addition_symbol` 로 따로 옵니다.** ISBN 필드에 섞여 들어올 것이라 보고 잘라
  내는 방어 코드를 넣었는데, 적어도 이 API 에서는 분리되어 있습니다. 방어는 그대로 두되
  (다른 소스가 붙을 수 있으므로) 전제로 삼지는 않습니다.
- **권차는 `vol` 로 따로 옵니다.** 제목 꼬리에서 파싱하는 것보다 이 값이 믿을 만하므로
  있으면 우선합니다. 파싱은 값이 없을 때의 보조로 남깁니다.
- **표지 URL(`bookImageURL`)이 옵니다.** "1차에는 표지 없이" 결정을 다시 볼 수 있습니다.
- **`format=json` 을 지원합니다.** 다만 JSON 쪽 감싸는 구조가 문서에 없어 XML 을 씁니다.

### 제 가정이 맞았던 것

- 지역 코드 11=서울 외 16개 시도 전부
- 호출 URL 형식과 파라미터 이름
- 응답이 XML 이고 `libs > lib`, `docs > doc` 로 중첩된다는 것
- 세트 ISBN(`set_isbn13`)이 별도 항목이라는 것

## 2-1. 실제 응답을 받아 확인한 것 (2026-09-06)

네트워크 정책이 열려 처음으로 `data4library.kr` 에 실제 요청을 보냈습니다.
**인증키가 아직 활성화되지 않은 상태**라 정상 데이터는 못 받았지만, 그 과정에서
설계를 무너뜨릴 뻔한 것을 찾았습니다.

### 정보나루는 오류도 HTTP 200 으로 돌려줍니다

실제로 받은 본문입니다.

```
GET /api/libSrch?authKey=...&region=11        → HTTP 200
<response><errCode>vitalizationErr</errCode><error>API 활성화 상태가아닙니다.</error></response>

GET /api/libSrch?authKey=abc123&region=11     → HTTP 200
<response><errCode>authErr</errCode><error>인증정보가 일치하지 않습니다.</error></response>
```

**이 본문에는 `lib` 도 `doc` 도 없습니다.** 상태 코드만 보고 넘기면 파서가 빈 목록을
돌려주고, 화면은 그것을 **"미소장"으로 그립니다.** 정보나루가 흔들릴 때마다 멀쩡히
소장된 책이 전부 "없음"으로 나오는 것이고, 이 도구의 존재 이유가 무너지는 지점입니다.

`Data4LibraryResponse.errorOf` 로 본문을 먼저 검사하고 `ApiErrorException` 을 던지도록
고쳤습니다. 테스트에는 **실제로 받은 본문 그대로** 넣어 두었습니다.

### 오류 형식이 엔드포인트마다 다릅니다

같은 오류인데 `libSrch` 는 XML, `srchBooks` 는 JSON 으로 돌려주었습니다.

```
libSrch    → <response><errCode>vitalizationErr</errCode>...
srchBooks  → {"response":{"errCode":"vitalizationErr",...}}
```

`format` 을 지정하지 않았는데도 그렇습니다. 그래서 오류 검사는 두 형태를 모두 봅니다.
**정상 응답의 기본 형식도 엔드포인트마다 다를 수 있으므로, 키가 활성화되면 가장 먼저
확인해야 합니다.**

### 우리 쪽 요청이 나가지도 못하고 있었습니다

`User-Agent` 에 한글을 넣어 두었습니다. **HTTP 헤더 값은 ASCII 만 허용하므로** 자바가
요청을 만들다가 `IllegalArgumentException` 을 던졌고, 그래서 정보나루에 요청이 단 한 번도
나가지 않았습니다.

이것이 특히 나쁜 이유는 **화면에는 그냥 "확인 불가"로 보인다**는 점입니다. 겉으로는
정보나루가 응답하지 않는 것과 구별되지 않아서, 실제로 배포했다면 원인을 찾는 데 한참
걸렸을 것입니다. 게다가 호출 예산은 요청을 만들기 전에 깎이므로 **아무것도 못 하면서
하루 한도만 줄어들고 있었습니다.**

실행해 보지 않으면 절대 드러나지 않는 종류입니다. 테스트는 가짜 `Transport` 를 쓰기 때문에
헤더를 만들어 보지 않습니다. `WimbConfigurationTest` 가 실제로 `HttpRequest` 를 만들어
보도록 해서 이 계열을 잡습니다.

### 인증 오류에는 한동안 부르지 않습니다

키가 없거나 활성화되지 않은 것은 사람이 고쳐야 낫는 상태라, 재시도해도 성공하지 않습니다.
그런데 여러 권 확인은 한 번에 수십 번을 부르므로, 막지 않으면 실패할 것이 뻔한 요청으로
남의 서버를 수십 번 두드립니다. `authErr` 와 `vitalizationErr` 를 만나면 5분간 부르지 않고
바로 같은 오류를 돌려줍니다. **실측으로 8줄 확인이 요청 8회에서 1회로 줄었습니다.**

### 인증키가 아직 활성화되지 않았습니다

`vitalizationErr` 는 키는 존재하지만 활성 상태가 아니라는 뜻입니다. 정보나루
마이페이지에서 신청 승인 상태를 확인해야 합니다. **이것이 지금의 크리티컬 패스입니다.**

## 3. 아직 확인하지 못한 것

- **정상 응답의 실제 모양.** 오류 응답만 받아 봤습니다. 항목 이름, 중첩 구조, 기본 형식
  (XML 인지 JSON 인지)을 **키가 활성화되는 즉시 확인해야 합니다.**
- **응답의 최상위 요소 이름.** 매뉴얼이 항목 이름과 중첩 구조는 밝히지만 루트는 적어 두지
  않았습니다. 그래서 파서를 루트에 의존하지 않게 만들었고, 루트가 무엇이든 읽힙니다.
  오류 응답의 루트는 `response` 였습니다.
- **1일 호출 한도 30,000건.** 매뉴얼이 아니라 검색 결과에 근거합니다.
- **정상 데이터.** 네트워크는 열렸지만 인증키가 활성화되지 않아 오류 응답만 받았습니다.
- **`bookDtlUrl` 이 무엇을 가리키는지.** 정보나루 자체 페이지일 가능성이 높습니다.
  도서관 OPAC 이라면 리다이렉트 템플릿 작업이 크게 줄어듭니다.

## 4. 여전히 내부적으로만 일관된 것

**테스트를 통과한다는 것이 실제 데이터를 잘 다룬다는 뜻은 아닙니다.**

`golden-pairs.tsv` 47쌍은 제가 직접 쓴 것입니다. 정밀도 1.000 은 **"코드가 제 판단과
일치한다"** 는 뜻이지 **"실제 도서관 데이터를 잘 처리한다"** 는 뜻이 아닙니다.

정규화 규칙(KORMARC 구분 기호 처리, 판본·각색 표기 목록, 저자 역할어)도 한국 서지 관례에
대한 일반 지식으로 만든 것이고 **실제 정보나루 레코드를 본 적이 없습니다.**
`authors` 필드가 실제로 `칼 세이건 지음 ; 홍승수 옮김` 형태로 오는지는 받아 봐야 압니다.

규모 추정의 복본율 1.3, ISBN 보유율 80% 도 제 가정이고 실측이 아닙니다.

## 왜 추측이 틀려도 피해가 작은가

**자바 코드에서 외부 API 형식을 아는 곳은 `kr.wimb.data4library` 패키지 하나뿐입니다.**
나머지는 인터페이스 뒤에 있습니다.

```
HoldingsLookup.HoldingsClient   — ISBN 과 지역 코드로 도서관부호 목록을 받음
Data4LibraryClient.Transport    — URI 로 응답 본문을 받음
SourceAdapter                   — 소스 형태의 레코드를 내보냄
```

## 잘못된 가정이 조용히 통과하지 않게 한 장치

- `HoldingsLookup` 은 매뉴얼대로 `PER_REGION` 으로 시작하되 **탐색 로직을 남겨 두어**,
  문서와 실제가 다르면 스스로 따라갑니다. 문서를 믿되 그것만 믿지는 않습니다.
- 빈 결과(미소장)와 조회 실패(확인 불가)를 타입에서부터 구분합니다.
- `librariesHolding` 은 `region` 없이 부르면 **호출 전에 막습니다.** 조용히 빈 결과를 받아
  미소장으로 오해하는 것을 예방합니다.
- `IndexVerifier` 는 ISBN 이 없는 문서, 검색되지 않는 문서, 저작 번호가 중복된 문서를 잡습니다.
