# 가정과 검증 상태

이 저장소의 코드가 어디까지 검증되었고 어디부터 추측인지 적어 둡니다.

**2026-09-05 갱신:** 정보나루 Open API Manual (v20260210) 을 확보해 3번 항목이 대부분
사실로 바뀌었습니다. 아래 "매뉴얼로 밝혀진 것" 을 보세요.

**2026-09-08 갱신:** 인증키로 직접 불러 보았습니다. 정상 응답의 모양이 사실로 바뀌었고,
그 대신 **사용자가 겪은 증상 셋**이 3번에 새로 들어왔습니다. 원인은 코드에서 찾아 고쳤지만
호출 한도에 걸려 실제 응답으로 확인하지 못했으므로, **「고쳤다」가 아니라 「고쳤을
것이다」입니다.**

## 2. 매뉴얼로 밝혀진 것 (v20260210)

문서에 근거가 있으므로 추측이 아닙니다. 다만 **실제 응답을 받아 본 것은 아닙니다.**

### 계획이 바뀐 것

**`libSrchByBook` 의 `region` 은 필수입니다.** 전국을 한 번에 받는 방법이 없습니다.
소장 조회는 선택한 도서관들이 걸친 시도 수만큼 호출이 곱해집니다.
30권 × 판본 3개 × 시도 2곳이면 180회입니다.

**`libSrch` 가 위도와 경도를 줍니다.** 계획서는 위경도를 얻으려고 공공데이터포털의
전국도서관표준데이터를 받아 이름과 주소로 대조하는 단계를 두었고, 표준데이터에 도서관부호가
없어 그 대조를 **계획 전체에서 가장 큰 위험**으로 꼽았습니다. 정보나루가 코드와 위경도를
함께 주므로 **그 단계가 통째로 필요 없어집니다.**

**정보나루 하나로 1차 범위가 채워집니다.**

| 필요한 것 | 어디서 |
|---|---|
| 도서관 마스터 (코드·주소·위경도·홈페이지·휴관일·운영시간) | `libSrch` |
| 서지 (제목·저자·출판사·ISBN·세트ISBN·표지·대출건수) | `srchBooks` |
| 소장 도서관 | `libSrchByBook` |

국립중앙도서관 서지정보 API 와 공공데이터포털은 **서지 품질 보강용으로 나중에** 붙이면 됩니다.
1차를 시작하는 데 필요하지 않습니다.

### 제 가정이 틀렸던 것

- **부가기호는 `addition_symbol` 로 따로 옵니다.** ISBN 필드에 섞여 들어올 것이라 보고 잘라
  내는 방어 코드를 넣었는데, 적어도 이 API 에서는 분리되어 있습니다. 방어는 그대로 두되
  (다른 소스가 붙을 수 있으므로) 전제로 삼지는 않습니다.
- **권차는 `vol` 로 따로 옵니다.** 제목 꼬리에서 파싱하는 것보다 이 값이 믿을 만하므로
  있으면 우선합니다. 파싱은 값이 없을 때의 보조로 남깁니다.
- **표지 URL(`bookImageURL`)이 옵니다.** "1차에는 표지 없이" 결정을 다시 볼 수 있습니다.
- **`format=json` 을 지원합니다.** 다만 JSON 쪽 감싸는 구조가 문서에 없어 XML 을 씁니다.

### 제 가정이 맞았던 것

- 지역 코드 11=서울 외 16개 시도 전부
- 호출 URL 형식과 파라미터 이름
- 응답이 XML 이고 `libs > lib`, `docs > doc` 로 중첩된다는 것
- 세트 ISBN(`set_isbn13`)이 별도 항목이라는 것

## 2-1. 실제 응답을 받아 확인한 것 (2026-09-06)

네트워크 정책이 열려 처음으로 `data4library.kr` 에 실제 요청을 보냈습니다.
**인증키가 아직 활성화되지 않은 상태**라 정상 데이터는 못 받았지만, 그 과정에서
설계를 무너뜨릴 뻔한 것을 찾았습니다.

### 정보나루는 오류도 HTTP 200 으로 돌려줍니다

실제로 받은 본문입니다.

```
GET /api/libSrch?authKey=...&region=11        → HTTP 200
<response><errCode>vitalizationErr</errCode><error>API 활성화 상태가아닙니다.</error></response>

GET /api/libSrch?authKey=abc123&region=11     → HTTP 200
<response><errCode>authErr</errCode><error>인증정보가 일치하지 않습니다.</error></response>
```

**이 본문에는 `lib` 도 `doc` 도 없습니다.** 상태 코드만 보고 넘기면 파서가 빈 목록을
돌려주고, 화면은 그것을 **"미소장"으로 그립니다.** 정보나루가 흔들릴 때마다 멀쩡히
소장된 책이 전부 "없음"으로 나오는 것이고, 이 도구의 존재 이유가 무너지는 지점입니다.

`Data4LibraryResponse.errorOf` 로 본문을 먼저 검사하고 `ApiErrorException` 을 던지도록
고쳤습니다. 테스트에는 **실제로 받은 본문 그대로** 넣어 두었습니다.

### 오류 형식이 엔드포인트마다 다릅니다

같은 오류인데 `libSrch` 는 XML, `srchBooks` 는 JSON 으로 돌려주었습니다.

```
libSrch    → <response><errCode>vitalizationErr</errCode>...
srchBooks  → {"response":{"errCode":"vitalizationErr",...}}
```

`format` 을 지정하지 않았는데도 그렇습니다. 그래서 오류 검사는 두 형태를 모두 봅니다.
**정상 응답의 기본 형식도 엔드포인트마다 다를 수 있으므로, 키가 활성화되면 가장 먼저
확인해야 합니다.**

### 우리 쪽 요청이 나가지도 못하고 있었습니다

`User-Agent` 에 한글을 넣어 두었습니다. **HTTP 헤더 값은 ASCII 만 허용하므로** 자바가
요청을 만들다가 `IllegalArgumentException` 을 던졌고, 그래서 정보나루에 요청이 단 한 번도
나가지 않았습니다.

이것이 특히 나쁜 이유는 **화면에는 그냥 "확인 불가"로 보인다**는 점입니다. 겉으로는
정보나루가 응답하지 않는 것과 구별되지 않아서, 실제로 배포했다면 원인을 찾는 데 한참
걸렸을 것입니다. 게다가 호출 예산은 요청을 만들기 전에 깎이므로 **아무것도 못 하면서
하루 한도만 줄어들고 있었습니다.**

실행해 보지 않으면 절대 드러나지 않는 종류입니다. 테스트는 가짜 `Transport` 를 쓰기 때문에
헤더를 만들어 보지 않습니다. `WimbConfigurationTest` 가 실제로 `HttpRequest` 를 만들어
보도록 해서 이 계열을 잡습니다.

### 인증 오류에는 한동안 부르지 않습니다

키가 없거나 활성화되지 않은 것은 사람이 고쳐야 낫는 상태라, 재시도해도 성공하지 않습니다.
그런데 여러 권 확인은 한 번에 수십 번을 부르므로, 막지 않으면 실패할 것이 뻔한 요청으로
남의 서버를 수십 번 두드립니다. `authErr` 와 `vitalizationErr` 를 만나면 5분간 부르지 않고
바로 같은 오류를 돌려줍니다. **실측으로 8줄 확인이 요청 8회에서 1회로 줄었습니다.**

### 인증키가 아직 활성화되지 않았습니다

`vitalizationErr` 는 키는 존재하지만 활성 상태가 아니라는 뜻입니다. 정보나루
마이페이지에서 신청 승인 상태를 확인해야 합니다.

**이것은 그때의 이야기이고, 키는 그 뒤 활성화되었습니다.** 코드는 그대로 두었습니다.
키를 새로 발급받거나 옮길 때 같은 상태를 다시 만나기 때문입니다.

## 2-2. 인증키로 직접 불러 확인한 것 (2026-09-08)

### 정상 응답을 실제로 받았습니다

키가 활성화되어 서지를 받아 화면에 그리는 것까지 확인했습니다. **아래는 2-1 을 쓸 때
「아직 확인하지 못한 것」에 있던 항목들인데, 이제 사실로 바뀌었습니다.**

- **정상 응답의 실제 모양.** 응답은 XML 이고 `docs > doc` 로 중첩됩니다. `authors` 는
  가정대로 `지음 ; 옮김` 형태로 오지만 **구분 기호 주변 공백이 제각각입니다.** 같은 책의
  다른 판이 서로 다르게 옵니다. `RealResponseShapeTest` 가 실제로 받은 문자열로 고정합니다.
- **최상위 요소 이름.** 정상 응답도 오류 응답과 같이 `response` 였습니다. 파서는 여전히
  루트에 의존하지 않으므로 바뀌어도 읽힙니다.
- **권차와 부가기호가 따로 옵니다.** `vol` 과 `addition_symbol` 입니다. 제목에서 파싱하기
  전에 이 값을 먼저 봐야 합니다.

### 아무것도 안 나오던 진짜 원인은 코드가 아니었습니다

    {"errCode":"outOflimit",
     "error":"1일 500건 이상 요청 시 IP 등록이 필요합니다. 등록 된 IP를 확인하시기 바랍니다."}

검색도 도서관 목록도 전부 이것이었습니다. 정보나루 사이트에는 그날 1,410건으로 찍혀
있었는데, 500 은 넘고 30,000 은 한참 안 됩니다. **등록된 IP 로 인정받지 못하고 있다는
뜻입니다.**

**이것을 알아내는 데 하루를 썼습니다.** 정보나루는 이유를 한국어로 또박또박 알려 주고
있었는데, 그 문장이 서버에서 멈추고 화면에는 「API 오류 503」만 떴기 때문입니다. 그래서
원인을 코드에서 찾았고 여러 곳을 헛짚었습니다. `ApiErrorAdvice` 와 `/api/diagnose` 가
이제 그것을 막습니다.

### 하루 1,410건의 절반 이상은 우리가 만든 헛호출이었습니다

도서관 마스터를 못 받으면 목록이 비는데, **목록이 비어 있으면 재시도 빗장을 건너뛰고
있었습니다.** 정보나루가 답하지 않는 동안에는 목록이 늘 비어 있으므로, 화면을 한 번 열
때마다 전국 한 번 + 시도 열일곱 번을 다시 불렀습니다. **가장 안 될 때 가장 많이 부르는
셈**이고, 그 헛호출이 한도를 갉아먹어 고장이 스스로를 키웁니다.

## 2-3. 증상 셋을 실제 응답으로 확인했습니다 (2026-09-08, 2차)

한도가 풀린 뒤 배포된 서버(`5085ad1`)를 통해 실제로 불렀습니다. **코드를 보기 전에
`/api/diagnose` 를 먼저 열었고**, `egressIp` 가 `104.154.172.147`, `data4library` 가 `ok`,
남은 호출이 24,994건인 것을 확인한 다음에 시작했습니다.

### 1) 「마의 산」 — 정보나루는 줍니다. 우리가 화면에서 지우고 있었습니다

| 질의 | `foundBooks` | 돌려준 저작 수 |
|---|---|---|
| `title=마의 산` | 35 | 15 |
| `title=마의산` | 35 | 15 |
| `publisher=을유문화사` | 300 | 100 |

**0이 아닙니다.** 그러므로 「정보나루가 그 책을 못 준다」는 가설은 사실이 아니고, 원인은
우리 쪽에 있습니다.

을유문화사 판(`9788932403311`, `9788932403328`)은 없어진 것이 아니라 **다른 저작 안에
들어가 있었습니다.** 검색이 돌려준 저작 하나가 아래 열 판을 모두 품고 있습니다.

| ISBN | 실제 출판사 |
|---|---|
| 9788908070288, 9788908070295 | 범우사 |
| **9788932403311, 9788932403328** | **을유문화사** |
| 9788932916453, 9788932916460, 9788932916477 | 열린책들 |
| 9788949704128 | 동서문화사 |
| 9788962282498, 9788966803460 | 지식을만드는지식 |

**출판사 다섯 곳의 서로 다른 번역본 열 판이 한 저작입니다.** 그런데 화면에 나가는 것은
대표로 뽑힌 「열린책들」 하나뿐이고, `editionLabels` 는 비어 있습니다. 을유문화사 판을
찾는 사람에게 이 화면은 **「그 책이 없다」와 구별되지 않습니다.**

병합 근거는 R3(`표제 키 + 저자` 일치)이며, **이 규칙은 출판사를 보지 않습니다.** 표제가
「마의 산」이고 저자가 「토마스 만」이면 어느 번역본이든 같은 저작이 됩니다. 고장이 아니라
규칙대로 동작한 것입니다.

**문제는 결과가 권차를 버렸을 때와 같은 모양이라는 점입니다.** 낱권 다섯이 한 저작으로
합쳐졌을 때 「1권만 있는 도서관이 레미제라블 있음으로 나온다」고 적었는데, 여기서는
**범우사 판만 있는 도서관이 「마의 산(열린책들) 있음」으로 나옵니다.** 번역서는 판이
다르면 읽는 사람에게 다른 책이고, 이 문서의 다른 자리에도 「사용자가 찾는 것은 대개
자기가 아는 그 판」이라고 적혀 있습니다.

### 2) 레미제라블 — 권차 분리는 동작합니다. 낱권이 안 나오는 이유는 따로 있었습니다

**고친 것은 실제로 동작합니다.** `q=레미제라블` 이 「레미제라블 1권」 「2권」 「3권」
「4권」을 각각 다른 저작으로 돌려줍니다. 정보나루가 `vol` 을 준다는 것과, 그것이
`displayTitle` 까지 이어진다는 것이 함께 확인되었습니다.

**그런데 사용자가 본 증상은 그대로 남아 있고, 원인이 권차가 아니었습니다.**

| 질의 | `foundBooks` | 결과 |
|---|---|---|
| `q=레미제라블` + `publisher=민음사` | **1** | 「레미제라블 세트 - 전5권」뿐 |
| `q=레 미제라블` + `publisher=민음사` | **8** | 낱권 1~5권과 12권 |

민음사 낱권의 서명은 **「레 미제라블」로 띄어져 있습니다.** 정보나루의 `title` 검색은
**공백을 무시하지 않으므로**, 「레미제라블」로는 낱권이 한 건도 걸리지 않습니다. 세트만
붙여 쓴 표기라서 세트만 나왔던 것입니다.

우리에게는 대비가 하나 있지만 이 경우에 닿지 않습니다. `respacedTitle` 은 **0건일 때만**
발동하고 **공백을 빼는 방향**뿐인데, 여기서는 세트 1건이 잡혀 0건이 아니고 필요한 것은
**공백을 넣는 방향**입니다.

**그리고 「마의 산」의 두 질의가 같은 35건을 준 것과 이 결과는 서로 어긋납니다.** 「마의산」은
공백 없이도 「마의 산」을 찾아냈는데 「레미제라블」은 「레 미제라블」을 못 찾았습니다.
사례를 더 모아 아래 2-4 에 적었습니다.

`q=레미제라블` 한 번에서 `droppedNoIsbn` 이 **49건 중 15건**이었습니다. ISBN 을 판별하지
못해 버린 것인데, 세 건에 한 건꼴이라 그냥 넘길 숫자가 아닙니다.

### 3) 소장 조회 — 고친 것이 실제로 동작합니다

「레 미제라블 1권」(민음사, `9788937444494`·`9788937463013`)을 **서울 359곳 전체**를 고른
상태로 조회했습니다.

- **179곳**이 소장으로 잡혔고 `complete: true`, `unreadable: false` 였습니다.
  한 쪽으로는 나올 수 없는 수이므로 **`numFound` 쪽 넘김이 실제로 돌고 있습니다.**
- **다른 엔드포인트로 대조했습니다.** 소장으로 잡힌 3곳과 잡히지 않은 3곳을 골라

## 2-4. 정보나루의 제목 매칭을 사례로 좁혔습니다 (2026-09-08, 3차)

`keyword` 를 서버에 열어 배포한 뒤(`f95597c`) 실제로 불러 확인했습니다.

### `keyword` 는 제목 검색의 대체가 아닙니다

매뉴얼 16절이 `title` 과 별개 항목으로 두고 있어 기대했지만, **주제어 검색이었습니다.**

| 질의 | `foundBooks` | 돌아온 것 |
|---|---|---|
| `keyword=레미제라블` | 47 | 「아주 사적인, 긴 만남」 「세계 도서관 기행」 「장발장」 |
| `keyword=마의 산` | 4 | 「마의」 「모던걸의 명랑 만세」 |
| `keyword=마의산` | 0 | |

**제목이 「레미제라블」인 책도 「마의 산」인 책도 한 권도 돌아오지 않았습니다.** 책 소개나
주제에 그 말이 나오는 책을 찾아 줍니다. 공백 문제를 풀지 못할 뿐 아니라 제목 검색보다
나쁩니다. **`keyword` 를 제목 검색에 쓰지 마세요.** 세미콜론으로 나누는 `레;미제라블` 도
0건이었습니다.

### `title` 은 어절의 앞에서부터 맞춥니다

민음사와 을유문화사로 좁혀 놓고 조각을 바꿔 가며 불렀습니다.

| 질의 | 결과 | 서명 안에서의 자리 |
|---|---|---|
| `미제라블` | **8건** (낱권 전부) | 「레 **미제라블**」의 둘째 어절 전체 |
| `제라블` | 0건 | 어절 중간부터 |
| `레 미제` | 0건 | 어절을 걸치면서 뒤가 잘림 |
| `마의` | **2건** | 「**마의** 산」의 첫 어절 전체 |
| `의 산` | 0건 | 어절 중간부터 |

**어절 중간에서 시작하는 조각은 잡히지 않습니다.** 어절 하나를 통째로 주면 잡힙니다.
그래서 「레미제라블」이 「레 미제라블」을 못 찾습니다. 어느 어절과도 맞지 않기 때문입니다.

**다만 이 규칙만으로 「마의산」이 「마의 산」을 찾아낸 것은 설명되지 않습니다.** 「마의산」은
「마의 산」의 어느 어절도 아닙니다. 한국어 형태소 분석이 「마의산」을 「마의」와 「산」으로
쪼개는 반면 「레미제라블」은 외래어라 쪼개지 못한다고 보면 앞뒤가 맞지만, **이것은 아직
추측이고 정보나루 안쪽 일이라 확인할 방법이 없습니다.** 어느 쪽이든 우리가 할 일은
같습니다. **제목 매칭을 믿을 수 있는 것으로 다루지 마세요.**

### 그래서 「양쪽 표기로 함께 찾기」는 그대로는 안 됩니다

「레미제라블」에서 「레 미제라블」을 만들려면 **공백을 어디에 넣을지 알아야 하는데 알 수가
없습니다.** 앞 글자를 떼는 방법(`미제라블`)은 출판사까지 좁혔을 때는 8건으로 정확했지만
제목만으로는 196건 157저작이 나와 쓸 수 없습니다.

**쓸 만한 것이 하나 있습니다. 찾은 책의 저자로 되찾는 것입니다.**
`author=빅토르 위고` 와 `publisher=민음사` 로 11건이 왔고 거기에 낱권이 전부 있었습니다.
같이 온 「파리의 노트르담」은 표제 정규화 키가 다르므로 걸러집니다. 「레미제라블」과
「레 미제라블」은 `normalizeKey` 가 공백을 지우므로 **키가 같아집니다.** 첫 검색으로 저자를
알아낸 다음 그 저자로 한 번 더 찾고, 키가 맞는 것만 더하면 호출은 두 번으로 끝납니다.
**아직 구현하지 않았습니다.**

## 3. 아직 확인하지 못한 것

- **우리가 물어보는 ISBN 목록이 완전하지 않습니다.** 검색 한 번에서 받은 서지로 저작을
  묶으므로, 도서관이 그 응답에 없던 옛날 판을 가지고 있으면 **물어보지도 못합니다.**
  `CLAUDE.md` 가 「임시 구조」라고 못 박아 둔 부분이고, 적재와 색인을 돌려야 없어집니다.
- **`droppedNoIsbn` 으로 빠지는 자료가 무엇인지.** 레미제라블에서 49건 중 15건이었는데,
  어떤 자료가 왜 빠지는지는 숫자만으로 알 수 없습니다.
- **정보나루의 `title` 매칭 규칙.** 바로 위 2-3 의 2)에 적은 대로 두 사례가 서로
  어긋납니다. **모르는 채로 두고, 아는 척하지 마세요.**

### 정보나루에 대해 아직 모르는 것

위의 세 항목과 성격이 다릅니다. 위는 **우리 코드에 고칠 대상이 있는 것**이고, 이쪽은
**정보나루에 대해 우리가 모르는 것**이라 물어보거나 사례를 모아야 합니다.

- **1일 호출 한도 30,000건.** 매뉴얼이 아니라 검색 결과에 근거합니다. 등록되지 않은 IP 의
  500건 한도는 오류 메시지로 확인했지만, 등록된 IP 의 상한은 아직 눈으로 못 봤습니다.
  `/api/diagnose` 가 말하는 남은 건수는 **우리 원장이 센 숫자일 뿐이라 근거가 되지

  도서관 OPAC 이라면 리다이렉트 템플릿 작업이 크게 줄어듭니다.

## 왜 추측이 틀려도 피해가 작은가

**자바 코드에서 외부 API 형식을 아는 곳은 `kr.wimb.data4library` 패키지 하나뿐입니다.**
나머지는 인터페이스 뒤에 있습니다.

```
HoldingsLookup.HoldingsClient   — ISBN 과 지역 코드로 도서관부호 목록을 받음
Data4LibraryClient.Transport    — URI 로 응답 본문을 받음
SourceAdapter                   — 소스 형태의 레코드를 내보냄
```

## 잘못된 가정이 조용히 통과하지 않게 한 장치

- `HoldingsLookup` 은 매뉴얼대로 `PER_REGION` 으로 시작하되 **탐색 로직을 남겨 두어**,
  문서와 실제가 다르면 스스로 따라갑니다. 문서를 믿되 그것만 믿지는 않습니다.
- 빈 결과(미소장)와 조회 실패(확인 불가)를 타입에서부터 구분합니다.
- `librariesHolding` 은 `region` 없이 부르면 **호출 전에 막습니다.** 조용히 빈 결과를 받아
  미소장으로 오해하는 것을 예방합니다.
- `IndexVerifier` 는 ISBN 이 없는 문서, 검색되지 않는 문서, 저작 번호가 중복된 문서를 잡습니다.
