# 문서 챙기기

이 저장소의 문서는 넷이 서로 다른 일을 합니다. **어디에 적느냐가 내용만큼 중요합니다.**
같은 사실을 엉뚱한 문서에 적으면 아무도 그것을 읽지 않는 자리에 놓이게 됩니다.

## 1. 무엇이 바뀌었는지 먼저 봅니다

```bash
git diff --name-only HEAD~1 HEAD   # 이번에 커밋한 것
git status --short                 # 아직 커밋하지 않은 것
```

동작이 달라지지 않았으면 문서를 고치지 않습니다. **오탈자, 포매팅, 결과가 같은
리팩터링은 문서를 건드릴 일이 아닙니다.** 사실이 달라졌을 때만 고칩니다.
문구를 다듬으려고 고치기 시작하면 무엇이 실제로 달라졌는지가 기록에서 사라집니다.

## 2. 어디에 적나

| 무엇이 달라졌나 | 고칠 문서 | 적을 것 |
|---|---|---|
| 외부 API 의 실제 응답을 눈으로 확인했다 | `docs/가정과-검증상태.md` | 추측이던 줄을 확인으로 옮기고, **언제 무엇으로 확인했는지** |
| 확인해 보니 가정이 틀렸다 | 위 + `CLAUDE.md` | 무엇을 잘못 가정했고, 그것 때문에 **어디가 조용히 틀렸는지** |
| 되풀이해서 어길 만한 제약이 생겼다 | `CLAUDE.md` | 「하지 마세요」가 아니라 **어기면 무엇이 조용히 틀리는지** |
| 예전 결정을 뒤집었다 | `CLAUDE.md` | **뒤집었다는 사실 자체를.** 안 적으면 다음 세션이 예전 규칙대로 되돌립니다 |
| 되는 것과 안 되는 것이 달라졌다 | `README.md` 「지금 어디까지 되는가」 | 되는 것뿐 아니라 **아직 안 되는 것도** |
| 새 화면이나 엔드포인트가 생겼다 | `README.md` 「구조」 | |
| 배포·운영 절차가 달라졌다 | `docs/배포.md`, `scripts/vm/README.md` | 손으로 쳐야 하는 명령은 그대로 옮겨 적습니다 |
| 사람이 손으로 해야 할 일이 생겼다 | `docs/` 아래 별도 문서 | `docs/도서관-주소-규칙-채우기.md` 가 그 예입니다 |
| 「같은 책」의 판정이 틀린 사례를 만났다 | `backend/src/test/resources/bib/golden-pairs.tsv` | 이 파일이 명세입니다. 한 줄 추가하는 것이 문서 갱신입니다 |
| 계획과 실제가 갈렸다 | `docs/가정과-검증상태.md` | **`docs/구현계획.md` 는 고치지 않습니다.** 아래 4절 |

`CLAUDE.md` 는 **되풀이해서 어기기 쉬운 제약만** 모으는 자리입니다. 한 번 하고 끝나는
사실이나 배경 설명은 여기 말고 `README.md` 나 `docs/` 로 보냅니다. 이 문서가 길어질수록
정작 중요한 제약이 묻힙니다.

## 3. 어떻게 쓰나

**이유를 함께 적습니다.** 금지만 적어 두면 다음 사람이 정리하다가 되돌립니다.

> 호출을 `pace()` 의 잠금 안으로 옮기지 마세요. **그 순간 호출이 직렬화되어 왕복 시간이
> 그대로 쌓입니다.**

앞 문장만 있으면 「보기 안 좋은데 정리할까」가 되지만, 뒤 문장이 있으면 손대지 않습니다.

**확인한 것과 추측한 것을 섞지 않습니다.** 문서를 열어 봤는지, 실제로 호출해 봤는지,
그냥 그럴 것 같은지를 구분해서 적습니다. 이 구분이 무너지면 `docs/가정과-검증상태.md`
자체가 쓸모없어집니다.

**조용히 틀리는 것을 앞에 둡니다.** 눈에 보이는 실패는 알아서 발견됩니다. 정작 위험한
것은 HTTP 200 을 주면서 결과만 0건이 되는 쪽이고, 그런 것부터 적습니다.

**결정을 뒤집었으면 뒤집었다고 적습니다.** 예를 들어 대출 상태는 원래 「어떤 경우에도
표시하지 않는다」였다가 「누를 때만, 날짜와 함께 보여 준다」로 바뀌었습니다. 그 사실을
적어 두지 않으면 다음 세션이 예전 규칙을 읽고 기능을 지웁니다.

## 4. 계획 문서는 고치지 않습니다

`docs/구현계획.md` 는 착수 전에 세운 계획의 기록입니다. 지금 코드에 맞춰 고치면 무엇을
예상했고 실제로는 무엇이 달랐는지가 사라집니다. 그것이 이 저장소에서 가장 값나가는
기록입니다. `region` 이 필수였던 것, `libSrch` 가 위경도를 주는 것, 관종 필드가 없는 것은
전부 계획과 실제가 갈린 지점이고, 계획을 덮어썼으면 아무것도 남지 않았을 것입니다.

**이 스킬로는 그 제한을 풀 수 없습니다.** 훅은 도구를 부르는 단계에서 걸리므로 어떤 스킬이
켜져 있든 똑같이 막힙니다. Write 와 Edit 뿐 아니라 Bash 로 쓰려는 것도 막습니다.

정말 고쳐야 하면 둘 중 하나입니다.

- 사람이 직접 편집기로 고칩니다. 훅은 Claude 의 도구 호출에만 걸립니다.
- `/hooks` 에서 잠시 끕니다.

다만 **대부분의 경우 고칠 필요가 없습니다.** 계획과 달라진 것은 `docs/가정과-검증상태.md`
가 받고, 지금 지켜야 하는 규칙은 `CLAUDE.md` 가 받습니다. 계획 문서를 고치고 싶어졌다면
그 내용이 실은 저 둘 중 하나에 속하는 것은 아닌지 먼저 보세요.

## 5. 다 고쳤으면

문서 변경은 그것을 만든 코드 변경과 **같은 커밋**에 넣습니다. 따로 커밋하면 나중에
「이 규칙이 왜 생겼지」를 코드에서 찾을 수 없게 됩니다.
